GlueSQL test suite를 SQL fixture로 재구성했습니다

어제 글에서는 GlueSQL의 line coverage가 알려주는 것과 놓치는 것을 살펴봤습니다. coverage는 테스트가 어떤 코드를 실행했는지 보여주지만, test suite가 얼마나 읽기 쉽고 관리하기 좋은지는 알려주지 않습니다.

이번에는 GlueSQL의 SQL 기반 integration test 184개를 Rust test body에서 .sql fixture로 옮겼습니다. Pull Request #1941에 반영된 이 작업은 테스트 형식만 바꾼 것이 아니라, test suite가 검증과 문서의 역할을 함께 할 수 있도록 구조를 다시 잡은 작업입니다.

integration test를 읽을 수 있는 문서로 남기기

테스트는 regression을 찾는 장치이면서 프로젝트가 어떤 입력에 어떻게 동작하는지를 기록하는 문서이기도 합니다.

Unit test는 모듈 내부의 함수나 자료 구조를 직접 다루기 때문에 해당 구현의 문맥을 알아야 이해되는 경우가 있습니다. 반면 integration test는 여러 모듈을 거쳐 나타나는 실제 동작을 확인합니다. 입력과 실행 순서, 예상 결과가 드러날수록 기능의 사용 방법과 현재 동작을 파악하기 쉽습니다.

그래서 integration test는 기계가 반복해서 실행할 수 있어야 할 뿐만 아니라, 테스트를 추가하고 리뷰하는 사람에게도 읽기 좋은 형태여야 합니다.

Rust test body에서 SQL fixture로

기존 테스트에서는 실행할 SQL과 예상 결과를 Rust 코드로 구성했습니다.

g.test(
    "SELECT id, name FROM Foo WHERE id > 1",
    Ok(select!(
        id  | name
        I64 | Str;
        2     "Alice".to_owned();
        3     "Bob".to_owned()
    )),
);

SQL의 동작을 확인하려면 test harness와 select! macro, GlueSQL의 Value type을 함께 읽어야 했습니다. 테스트를 추가할 때도 SQL 바깥의 Rust 표현을 작성해야 했습니다.

이제는 실행할 SQL과 예상 결과를 같은 .sql 파일에 이어서 기록합니다.

-- @name: selected rows are returned in order
SELECT id, name FROM Foo WHERE id > 1 ORDER BY id;
-- @expect:
-- | id: I64 | name: Str |
-- | ------- | --------- |
-- | 2       | "Alice"   |
-- | 3       | "Bob"     |

위에서 아래로 SQL을 실행하고 각 SQL 바로 아래에 있는 결과를 비교합니다. 테이블 생성과 데이터 입력, 조회와 오류 확인을 한 파일에 순서대로 적을 수 있어 하나의 실행 시나리오처럼 읽을 수 있습니다.

가독성을 test suite의 규칙으로 만들기

기존 select! macro도 결과를 표와 비슷하게 작성할 수 있었습니다. 다만 Rust macro는 token을 기준으로 코드를 해석하므로 공백과 열 너비가 결과에 영향을 주지 않습니다. 값의 type과 구조는 확인할 수 있어도 각 값이 header 아래에 정렬되어 있는지, 모든 행이 같은 간격을 사용하는지까지 강제하기는 어렵습니다.

SQL fixture runner는 파일의 원문을 직접 읽기 때문에 예상 결과의 형식도 검사할 수 있습니다.

  • 모든 행의 column 수가 같은지 확인합니다.
  • 각 column에서 가장 긴 값을 기준으로 너비와 padding을 계산합니다.
  • header와 결과를 구분하는 separator row를 요구합니다.
  • canonical spacing과 맞지 않는 표는 테스트를 실패시킵니다.

표가 읽기 좋은지는 더 이상 작성자의 주의에만 맡겨두는 convention이 아닙니다. test suite가 계속 확인하는 규칙이 되었습니다.

fixture가 흐트러지지 않도록

파일이 늘어난 뒤에도 구조를 일정하게 유지할 수 있도록 다음 규칙을 함께 적용했습니다.

  • @name은 설명하는 SQL 바로 위에 둡니다.
  • @expect는 검증하는 SQL 바로 아래에 둡니다.
  • 모든 SQL step은 예상 결과와 함께 끝나야 합니다.
  • 새로 추가한 .sql fixture는 test case로 정확히 한 번 등록되어야 합니다.
  • 실패하면 fixture 경로와 line, step name, 실행한 SQL을 함께 표시합니다.

@expect에는 SQL이 성공해야 하는지, 어떤 오류가 발생해야 하는지, 조회 결과가 무엇인지 기록합니다. 실행할 SQL과 기대하는 동작을 한곳에서 읽을 수 있습니다.

Float 결과는 환경에 따라 아주 작은 차이가 생길 수 있으므로 F32와 F64를 각각 정해진 tolerance로 비교합니다. fixture에 지나치게 정밀한 값을 적지 않도록 허용하는 소수 자릿수도 parser에서 제한합니다. 개별 테스트마다 비교 방법을 다시 정하지 않고 runner 한곳에서 같은 정책을 적용합니다.

테스트를 더 쉽게 추가하기

일반적인 SQL 동작을 테스트할 때는 이제 Rust test harness를 먼저 이해하지 않아도 됩니다. 비슷한 fixture를 찾아 SQL과 예상 결과를 추가하면 같은 테스트가 GlueSQL의 여러 storage 구현에서 실행됩니다.

반대로 Rust API 자체를 확인하는 query builder 테스트와 storage를 직접 호출하는 테스트는 Rust에 남겼습니다. 모든 테스트를 한 형식에 맞추기보다, integration test로 읽을 수 있는 SQL 동작을 fixture로 옮기는 경계를 두었습니다.

복잡성이 사라진 것은 아닙니다. 여러 테스트에 흩어져 있던 parsing과 formatting, 값 비교와 오류 출력을 하나의 fixture runner가 담당하게 되었습니다. 대신 개별 테스트를 작성하는 사람은 작은 fixture 문법만 알면 됩니다. 관리할 규칙을 중앙에 모으고, 새로운 시나리오를 추가하는 비용을 낮춘 구조입니다.

SQL fixture는 테스트 결과를 저장하는 형식이 아니라, GlueSQL의 동작을 사람이 읽고 기계가 계속 검증하는 문서입니다.

미뤄둔 작업을 꺼내는 데 드는 시간

SQL fixture로 정리하면 test suite를 더 읽기 쉽고 관리하기 좋게 만들 수 있다는 생각은 이전부터 있었습니다. 다만 기존 테스트를 하나씩 옮기고 결과와 formatting을 확인하는 데 적지 않은 시간이 들 것으로 보여 쉽게 일정에 넣지는 못했습니다. 필요한 개선이라는 것과 실제로 시간을 배정할 수 있다는 것은 별개의 문제였습니다.

일주일이 필요한 작업을 매주 하나씩 끝내더라도 일 년에 할 수 있는 일은 52개뿐입니다. 실제로는 리뷰와 유지보수, 예상하지 못한 문제도 함께 처리해야 하므로 선택할 수 있는 작업은 더 적습니다. 오픈소스에는 이번 test suite 전환처럼 필요하다는 것을 알면서도 우선순위에서 밀려난 일이 계속 쌓입니다.

다음 글에서는 오픈소스에 기여할 일이 왜 현실적으로 계속 많을 수밖에 없는지 정리해보려고 합니다.
