오픈소스에는 생각보다 많은 기여 기회가 있습니다

어제 글에서는 필요하다는 것을 알면서도 일정에 넣지 못했던 GlueSQL 테스트 스위트 개선 작업을 소개했습니다. 일주일이 필요한 작업을 매주 하나씩 끝내더라도 일 년에 할 수 있는 일은 52개뿐이라는 이야기도 함께 남겼습니다.

이 숫자는 작업 하나가 특별히 어렵다는 뜻이 아닙니다. 작업 하나를 마치는 데 평일 5일이 걸린다고 해도 한 사람이 일 년 동안 처리할 수 있는 수에는 한계가 있다는 단순한 계산입니다. 실제로는 기존 코드 유지보수와 버그 대응, 리뷰와 릴리스도 함께 해야 하므로 새로운 작업에 사용할 수 있는 시간은 더 적습니다.

기여할 일이 없어서 남아 있지 않은 것이 아닙니다

처음 오픈소스 기여를 생각하면 이미 공개되어 오래 사용된 프로젝트에는 필요한 기능이 대부분 구현되어 있을 것처럼 보일 수 있습니다. 남아 있는 Issue는 아주 어렵거나, 프로젝트 전체를 이해해야만 다룰 수 있는 문제라고 생각하기도 쉽습니다.

하지만 많은 오픈소스 프로젝트의 꾸준한 유지보수는 소수의 메인테이너와 기여자를 중심으로 이루어집니다. 프로젝트에 필요하고 구현 가능한 작업이어도 당장 시간을 쓸 사람의 관심사와 우선순위에서 밀리면 다음 순서를 기다리게 됩니다. 오래 남아 있다는 사실만으로 그 작업이 중요하지 않거나 해결하기 어렵다는 뜻은 아닙니다.

필요한 일이 생기는 속도가 사람이 처리할 수 있는 속도보다 빠르면, 각각은 충분히 할 수 있는 작업이어도 기여 기회는 계속 남습니다.

작은 기능도 분명한 기여입니다

GlueSQL의 MAP과 LIST에는 내부 값을 선택하는 -> 연산자가 있습니다.

CREATE TABLE Users (profile MAP);
INSERT INTO Users VALUES ('{"name":"Han","role":"mentor"}');

SELECT profile->'name' AS name FROM Users;

이 ->는 Issue #1793에서 여러 JSON operator 가운데 첫 단계로 정리되었고, Pull Request #1807을 통해 추가되었습니다. 사용자 입장에서는 MAP에서 name을 꺼낸다는 결과를 바로 이해할 수 있고, SQL과 기대 결과도 짧게 표현할 수 있습니다.

GlueSQL이 사용하는 sqlparser는 ->, ->>, #>, #>> 같은 JSON operator를 이미 구분합니다. GlueSQL은 이 가운데 가장 기본적인 ->부터 MAP과 LIST에 연결했습니다. 나머지 operator도 각각 정해야 할 동작과 테스트는 있지만, parser나 전체 구조를 새로 만드는 작업은 아닙니다. sqlparser의 지원과 기존 -> 구현을 기준으로 하나씩 범위를 잡을 수 있습니다. 아직 구현되지 않은 이유도 특별히 어려워서라기보다, 다른 작업에 우선순위가 밀려 구현 순서를 기다리고 있기 때문입니다.

오픈소스 기여가 항상 새로운 데이터베이스 구조를 설계하거나 거대한 기능을 완성하는 일일 필요는 없습니다. 기존 기능을 참고해 빠진 동작을 추가하고, 오류가 발생하는 입력을 테스트로 남기고, 사용 방법을 문서에 보완하는 일도 프로젝트를 앞으로 움직입니다.

GlueSQL이 열어 둔 가능성

많은 데이터베이스 프로젝트는 주로 사용할 저장 방식과 환경, 처리할 workload를 정하고 그 목적에 맞게 기능을 발전시킵니다. 프로젝트의 목적과 맞지 않는 요구는 지원 범위 밖으로 둘 수 있습니다.

GlueSQL은 다양한 환경에서 같은 SQL interface를 사용할 수 있게 하는 방향을 열어 두고 있습니다. 하지만 메모리와 파일, 내장 데이터베이스, remote API는 데이터를 읽고 변경하는 방법뿐 아니라 지원 기능과 성능 특성도 서로 다릅니다.

GlueSQL의 planner와 executor는 특정 환경만을 전제로 하지 않으면서, 이런 차이가 있는 Storage에서도 같은 SQL을 처리할 수 있어야 합니다. 이론적으로 가능한 방향이지만 실제로 구현하려면 어떤 동작을 공통으로 다룰지, Storage의 차이를 어느 계층에서 처리할지, 지원하지 않는 기능을 어떻게 표현할지 계속 결정해야 합니다.

선택적인 Storage trait는 이 차이를 다루는 방법 중 하나입니다. 모든 Storage에 같은 구현을 요구하지는 않지만, 무엇을 공통 기능으로 두고 무엇을 선택 기능으로 둘지 설계하는 일은 남습니다. 새로운 환경이 추가될 때마다 기존 설계에서 미처 고려하지 못한 조건도 드러날 수 있습니다. GlueSQL의 Custom Storage 안내는 필요한 범위의 Storage trait부터 구현하는 방식을 설명합니다.

따라서 GlueSQL에는 planner와 executor의 경계를 다듬는 일부터 Storage별 기능, SQL 기능, 테스트와 문서를 보완하는 일까지 다양한 기여 기회가 생깁니다. 어려운 설계가 필요한 부분은 일부에 집중되어 있지만, 그 주변에는 범위가 분명한 작업도 계속 만들어집니다.

Issue로 다음 기여의 시작을 남기기

문제를 직접 구현하지 않아도 Issue로 남기는 일은 가치가 있습니다. 다음 내용이 있으면 막연한 요청을 다른 사람이 이어갈 수 있는 작업으로 바꿀 수 있습니다.

  • 어떤 입력이나 SQL에서 문제가 발생하는지
  • 현재 결과와 기대하는 결과가 무엇인지
  • 특정 환경의 문제인지 공통 기능의 문제인지
  • 비슷한 구현이나 관련 테스트를 어디에서 찾을 수 있는지

기존 Issue를 현재 코드에서 다시 확인하는 것도 기여입니다. 그동안 기능이 일부 구현되었는지, 재현 방법이 여전히 유효한지, 남은 범위를 더 작게 나눌 수 있는지 정리하면 다음 사람이 시작할 위치가 분명해집니다.

메인테이너가 모든 사용 환경과 관심사를 직접 경험할 수는 없습니다. 사용자가 발견한 불편과 원하는 동작을 공유하는 일은 프로젝트가 살펴볼 수 있는 범위를 넓혀 줍니다.

처음 기여할 작업을 찾는 방법

기여할 작업을 찾기 위해 프로젝트 전체를 먼저 이해할 필요는 없습니다.

  • 관심 있는 기능의 테스트를 읽고 현재 지원 범위를 확인합니다.
  • 직접 사용하며 예상과 다르게 동작하는 작은 입력을 찾습니다.
  • 비슷한 Issue가 있는지 확인하고 현재 코드에서도 재현되는지 살펴봅니다.
  • SQL과 기대 결과를 fixture로 작성해 변경할 동작의 경계를 정합니다.
  • 구현 범위가 애매하면 Issue에서 메인테이너와 먼저 이야기합니다.

GlueSQL의 SQL fixture는 입력과 기대 결과를 같은 파일에서 읽을 수 있어 이런 탐색의 시작점으로 사용할 수 있습니다. 구현보다 먼저 재현 가능한 테스트를 제안하는 것만으로도 문제를 훨씬 구체적으로 만들 수 있습니다.

AI가 바꾸는 실행 속도

AI가 등장하기 전에도 이 작업들은 대부분 이론적으로 가능했습니다. 문제는 가능한가보다 언제 시간을 배정할 수 있는가에 가까웠습니다.

낯선 저장소에서 관련 코드를 찾고, 비슷한 구현을 비교하고, 반복되는 수정을 적용하고, 테스트와 문서의 초안을 만드는 시간이 줄어들면 같은 기간에 시도할 수 있는 작업의 수가 달라집니다. 이전에는 다른 일에 밀려 선택하지 못했던 작업도 실제 구현 순서에 올릴 수 있습니다.

AI가 어떤 동작이 옳은지 결정하거나 검토의 책임을 대신하는 것은 아닙니다. 문제를 발견하고 기대하는 결과를 설명하며, 프로젝트의 방향에 맞는지 판단하는 일은 여전히 사람의 몫입니다. 다만 사람의 판단을 실제 코드와 테스트로 옮기는 속도는 이전과 달라지고 있습니다.

오픈소스에는 새로운 아이디어를 제안하는 일만큼, 필요하지만 아직 누군가의 시간을 받지 못한 일을 발견해 앞으로 옮기는 일도 중요합니다.

GlueSQL에서도 실행 속도가 빨라지면서, 이전에는 뒤로 미뤄 두었던 일들을 하나씩 실제 작업으로 옮길 수 있게 되었습니다.
