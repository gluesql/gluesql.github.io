보이지 않는 일이 코드를 오래 살게 합니다

새로운 기능은 비교적 알아보기 쉽습니다. 전에는 할 수 없던 일이 가능해지고, 사용자는 달라진 결과를 바로 확인할 수 있습니다. 반면 기존 규칙을 정리하고 예외를 줄이는 작업은 결과가 눈에 잘 띄지 않습니다. 아무것도 새로 생기지 않은 것처럼 보이거나, 성공했을 때 오히려 아무 일도 일어나지 않은 것처럼 보이기도 합니다.

2026년 8월 24일 Rust의 never 타입 안정화 Pull Request가 병합되었습니다. !를 완전한 타입으로 제안한 RFC 1216은 2015년에 시작되었고, tracking Issue #35121은 2016년에 열렸습니다. 마지막 안정화를 이끈 @WaffleLapkin은 다섯 번의 안정화 시도가 끝까지 이어지지 못한 뒤, 자신도 2년 넘게 이 작업을 해왔다고 짧은 글에 남겼습니다.

10년 뒤 바깥으로 드러난 변화는 ! 한 글자입니다. 하지만 이 작업의 가치는 새로운 문법 하나를 더한 데만 있지 않습니다. 언어 안에 함께 남아 있던 서로 다른 규칙을 정리하고, 기존 사용자가 새 규칙으로 이동할 수 있게 준비하고, 앞으로 같은 우회 방법을 반복하지 않아도 되게 한 데 있습니다.

눈에 보이는 변화는 ! 하나입니다

Rust의 !는 가능한 값이 하나도 없는 타입입니다. 별도의 결과를 돌려주지 않고 정상적으로 끝나는 함수는 ()를 사용합니다. ()에는 ()라는 값이 하나 있지만, !에는 만들 수 있는 값 자체가 없습니다.

그래서 호출한 곳으로 돌아오지 않는 함수는 다음처럼 표현할 수 있습니다.

fn wait_forever() -> ! {
    loop {}
}

panic!(), 프로세스 종료, 끝나지 않는 loop, return과 break처럼 현재 흐름을 벗어나는 표현식도 같은 성질을 가집니다. 값을 만들지 않기 때문에 !는 다른 타입이 필요한 위치에 놓일 수 있습니다.

Rust에는 이미 -> !처럼 이 성질을 사용하는 문법이 있었습니다. 새 안정화의 핵심은 !를 특별한 반환 표식으로만 두지 않고, 제네릭 코드와 타입 인자에서도 다른 타입처럼 사용할 수 있게 하는 것입니다. 안정화가 정식 버전에 도착하면 실패할 수 없는 결과를 다음처럼 직접 표현할 수 있습니다.

type CannotFail<T> = Result<T, !>;

Err 안에 넣을 ! 값을 만들 수 없으므로 CannotFail<T>는 Ok(T)만 가질 수 있습니다.

여기서 한 가지 질문이 생깁니다. 실패할 수 없다면 Result<T, !> 대신 그냥 T를 반환하면 되지 않을까요?

하나의 함수만 놓고 보면 맞습니다. 하지만 여러 구현이 같은 인터페이스를 따라야 할 때는 이야기가 달라집니다.

trait Source {
    type Error;

    fn read(&mut self) -> Result<String, Self::Error>;
}

파일에서 값을 읽는 구현은 I/O 오류가 발생할 수 있습니다. 반면 이미 메모리에 들어 있는 값을 반환하는 구현은 실패할 이유가 없습니다.

FileSource   -> Result<String, std::io::Error>
MemorySource -> Result<String, !>

!를 사용하면 호출하는 쪽은 두 구현을 같은 Result 방식으로 다룰 수 있습니다. 동시에 MemorySource가 실패하지 않는다는 사실도 타입에 남습니다. 실패하지 않는 경우만을 위해 별도의 인터페이스를 만들 필요도 없습니다.

지금까지는 variant가 하나도 없는 별도 enum이나 표준 라이브러리의 Infallible이 이 자리를 대신했습니다. Infallible도 만들 수 있는 값이 없기 때문에 같은 역할을 하지만, 라이브러리에서 별도 타입으로 마련한 표현입니다. !가 완전한 타입이 되면 같은 개념을 언어의 한 가지 규칙으로 설명할 수 있습니다.

사용자가 보게 될 변화만 놓고 보면 별도 타입 대신 !를 쓸 수 있다는 정도입니다. 이미 우회 방법이 있었으므로 급하게 해결해야 할 기능 부족처럼 보이지도 않습니다.

어려웠던 일은 문법을 허용하는 것이 아니었습니다

fn number_or_stop(ready: bool) -> u32 {
    if ready {
        42
    } else {
        panic!("not ready")
    }
}

if의 두 분기는 보통 같은 타입의 값을 만들어야 합니다. 위 코드에서 첫 번째 분기는 u32를 만들지만, panic!()을 호출한 분기는 값을 돌려주지 않고 실행을 끝냅니다. 이쪽에서 실제 값이 돌아올 일이 없으므로 전체 if 표현식은 u32로 볼 수 있습니다.

이처럼 주변에서 u32를 요구하는 경우에는 !가 놓일 자리가 분명합니다. 문제는 컴파일러가 주변 코드만 보고 어떤 타입이 필요한지 결정할 수 없는 경우였습니다. Rust 컴파일러는 오랫동안 이때 !를 ()로 추론하는 fallback을 사용했습니다. 실행이 이어지지 않는다는 의미가, 값 하나를 가진 unit 타입으로 바뀌는 예외 규칙이었던 셈입니다.

이 규칙을 !로 바로 바꾸면 의미는 더 자연스러워지지만, 기존 fallback에 기대던 제네릭 코드와 ? 표현식 일부는 더 이상 컴파일되지 않을 수 있습니다. 실제로 Rust 1.41을 목표로 한 안정화는 회귀가 발견되어 되돌려졌습니다.

그렇다고 기존 동작을 영구히 남긴 채 !만 타입으로 허용하면 언어에는 두 설명이 함께 남습니다.

  • !는 값이 존재하지 않는 타입입니다.
  • 단, 컴파일러가 타입을 정하지 못하면 값이 하나인 ()로 취급합니다.

이 두 규칙을 함께 유지할수록 컴파일러와 라이브러리 구현, 문서와 사용자 코드가 모두 예외를 기억해야 합니다. 새로운 기능을 빨리 제공하는 대신 이후의 작업이 계속 이 차이를 고려하도록 만들 수도 있습니다.

Rust는 2024 Edition의 never type fallback 변경에서 먼저 fallback을 !로 바꾸고, 영향을 받는 코드를 찾는 lint와 마이그레이션 안내를 제공했습니다. 이후 모든 Edition에 같은 fallback을 적용하고 Infallible을 !의 별칭으로 만들며, 이전 fallback을 전제로 하던 lint도 제거하는 순서로 나아갔습니다.

부채는 코드의 양보다 기억해야 할 규칙의 수에 쌓입니다

기술 부채를 코드가 지저분하거나 파일이 큰 상태로만 생각하기 쉽습니다. 하지만 서로 비슷한 두 타입이 같은 역할을 하고, 오래된 호환 규칙이 특정 경로에서만 적용되고, 새 기능을 만들 때마다 그 차이를 확인해야 하는 상태도 부채입니다.

이런 부채는 당장 동작하지 않는 버그가 아닐 수 있습니다. 각각의 경로에는 테스트가 있고 사용 중인 코드도 있습니다. 그래서 유지하는 편이 안전해 보입니다. 하지만 새 기능을 추가할 때마다 어느 규칙을 따라야 하는지 판단해야 하고, 한쪽만 수정하면 다른 쪽이 빠질 수 있습니다.

never 타입 안정화에서 정리한 것도 이런 차이였습니다.

함께 존재하던 개념 정리한 방향
diverging expression의 !와 완전한 타입으로서의 ! 하나의 타입으로 설명
타입을 정하지 못할 때 ()로 바꾸는 fallback !의 의미를 그대로 유지
별도 빈 enum인 Infallible !의 별칭으로 통합
이전 fallback 의존성을 찾는 임시 lint 마이그레이션 뒤 제거

여기서 lint와 Edition 단계는 최종 구조에 영원히 남길 기능이 아니라, 기존 생태계를 데리고 이동하기 위한 장치였습니다. 정돈은 과거의 선택을 잘못으로 규정하고 지우는 일이 아닙니다. 그 선택이 필요했던 이유를 확인하고, 더 이상 필요하지 않게 만드는 과정에 가깝습니다.

정돈의 결과는 아무 일도 일어나지 않는 모습으로 나타납니다

새 기능의 성공은 전에는 실패하던 예제가 동작하는 모습으로 보여줄 수 있습니다. 호환성과 정돈 작업의 성공은 반대로 나타납니다.

  • 기존 crate가 예상하지 못한 방식으로 깨지지 않습니다.
  • 영향을 받는 코드는 안정화 전에 경고를 통해 발견됩니다.
  • 마이그레이션이 끝난 뒤에는 임시 호환 경로와 lint를 제거할 수 있습니다.
  • 다음 컴파일러와 라이브러리 작업은 더 적은 예외를 전제로 시작합니다.

최종 PR에는 never 타입과 fallback 변경만이 아니라 실제 crate를 대상으로 한 호환성 실험, 회귀를 줄이기 위한 컴파일러 수정, Infallible을 !와 통합하기 위한 라이브러리 논의, 새 동작을 설명하는 문서 작업이 함께 연결되어 있습니다. 이 중 많은 일은 사용자가 직접 호출할 API를 만들지 않습니다. 오히려 사용자가 별다른 문제를 느끼지 않도록 하기 위한 작업입니다.

그래서 이런 기여는 크기를 알아보기 어렵습니다. 변경된 화면도 없고 벤치마크 숫자가 크게 오르지도 않습니다. 성공한 날에도 대부분의 Rust 코드는 전날과 똑같이 컴파일됩니다. 하지만 이후의 타입 시스템과 제네릭 라이브러리는 더 일관된 규칙 위에서 만들어질 수 있습니다.

AI는 기존 규칙을 더 빠르게 증폭합니다

AI 코딩 에이전트는 주변 코드에서 비슷한 구현을 찾고, 현재 발생한 오류를 고치고, 반복되는 변경을 여러 파일에 적용하는 일을 빠르게 할 수 있습니다. 이전 글에서는 이 실행 속도가 사람이 시간을 배정하지 못했던 오픈소스 작업을 앞으로 옮길 수 있다고 이야기했습니다.

같은 능력은 기존 코드의 부채도 빠르게 퍼뜨릴 수 있습니다. 코드베이스 안에 두 개의 비슷한 경로와 임시 우회 방법이 함께 있다면, AI는 그것이 역사적으로 남은 예외인지 앞으로 따라야 할 규칙인지 저절로 알지 못합니다. 주어진 테스트를 통과시키기 위해 이미 있는 분기를 복사하거나 그 위에 변환을 하나 더 얹는 선택은 가까운 문제를 해결하지만, 전체 규칙을 더 분명하게 만들지는 않습니다.

AI가 기술 부채를 만든다는 말이 AI가 언제나 잘못된 코드를 작성한다는 뜻은 아닙니다. 현재 작업의 목적이 누락된 동작 하나를 추가하는 데만 있다면, 에이전트도 그 범위에 맞춰 가장 가까운 해법을 찾습니다. 어떤 경로를 장기적으로 없앨지, 호환성 비용을 언제 감당할지, 여러 모듈이 함께 지켜야 할 규칙을 무엇으로 둘지는 별도의 판단입니다.

코드를 만드는 비용이 낮아질수록 이 판단은 더 중요해집니다. 좋지 않은 관습 하나가 더 많이 복제될 수도 있지만, 잘 정리된 타입과 API, 분명한 테스트 경계도 더 넓게 반복될 수 있기 때문입니다.

AI는 현재의 규칙을 빠르게 확장할 수 있습니다. 그래서 어떤 규칙을 남길 것인지 정하는 일은 이전보다 더 중요해졌습니다.

AI는 정돈 작업에도 유용합니다. 오래된 사용 경로를 검색하고, 영향을 받는 코드를 분류하고, 반복적인 마이그레이션과 테스트 초안을 준비할 수 있습니다. 다만 무엇을 추가할지만이 아니라, 어떤 예외와 우회 방법을 없앨지도 작업의 목표로 먼저 정해야 합니다.

다음 코드를 덜 복잡하게 만드는 기여

GlueSQL에서도 사용자에게 바로 보이는 SQL 기능만 프로젝트를 앞으로 움직이는 것은 아닙니다. 실행 파이프라인을 정리한 작업은 planner가 결정할 내용과 executor가 실행할 내용을 타입으로 나누었습니다. 이 작업의 가치는 새로운 SQL 문법을 추가한 데 있지 않았습니다. 이후 구현과 리뷰에서 같은 판단을 반복하지 않게 하는 기반을 마련했습니다.

최근 기여 사례를 살펴본 글의 HashJoinPlanner 이름 정리도 실행 결과를 바꾸지 않았습니다. 하지만 이름과 실제 책임을 맞추면서 다음 사람이 이름만 보고도 이 단계가 선택적인 최적화임을 알 수 있게 했습니다.

이런 변화는 변경량이나 새로운 기능의 수로는 충분히 설명되지 않습니다. 한 가지 개념을 여러 이름으로 부르던 상태를 정리하고, 임시 분기를 제거할 수 있는 마이그레이션을 만들고, 잘못된 패턴이 다시 들어오지 않게 테스트와 lint를 남기는 일은 다음 기여자의 비용을 낮춥니다.

오픈소스에서 인정받기 쉬운 결과는 대체로 눈에 보입니다. 새로운 기능, 빨라진 숫자, 닫힌 Issue가 그렇습니다. 반면 앞으로 필요할 설명의 수를 줄인 사람, 기존 사용자를 지키면서 예외를 없앤 사람, 다음 구현이 더 단순해질 기반을 만든 사람의 기여는 결과 안에 조용히 남습니다.

never 타입을 안정화한 뒤 @WaffleLapkin은 “I feel… empty. Just like the never type.”이라고 짧게 적었습니다. 10년의 역사와 자신이 보낸 2년을 길게 설명하는 대신 남긴 농담이었습니다.

그동안의 작업이 눈에 보이는 거대한 기능으로 나타난 것은 아닙니다. 이제 Rust는 값이 존재하지 않는다는 한 가지 개념을 더 적은 예외로 설명할 수 있게 되었습니다. 이후 Rust를 사용하는 사람은 그동안 쌓인 예외를 모두 알지 않아도 더 일관된 타입 규칙을 사용할 수 있습니다.

눈에 잘 띄지 않아도, 다음 사람이 불필요한 복잡성을 떠안지 않게 만드는 일은 코드를 오래 살게 합니다.
