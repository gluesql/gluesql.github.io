GlueSQL의 line coverage 98%를 읽는 법

GlueSQL은 핵심 코드의 line coverage를 98%대로 유지하고 있습니다. GlueSQL README에서도 거의 99%에 이르는 line coverage와 읽기 쉬운 test suite를 함께 소개합니다.

이 숫자는 대부분의 코드가 실제 테스트를 거쳤다는 유용한 신호입니다. 다만 코드의 98%가 정확하다거나, 발생할 수 있는 문제의 98%를 확인했다는 뜻은 아닙니다. coverage가 무엇을 측정하는지 알면 이 숫자를 더 적절하게 읽을 수 있습니다.

line coverage가 말하는 것

line coverage는 실행 가능한 코드 줄 가운데 테스트 중 한 번 이상 실행된 줄의 비율입니다. 테스트되지 않은 코드를 파일과 위치 단위로 찾고, 이전 결과나 Pull Request와 정량적으로 비교하기 쉽습니다.

하지만 한 줄이 실행됐다는 사실만으로 그 줄에 포함된 모든 조건과 입력을 확인했다고 말할 수는 없습니다.

한 줄 안에서 놓치는 실행 경로

GlueSQL에서 BETWEEN 표현식을 평가하는 코드에는 다음 조건문이 있습니다.

if target.is_null() || low.is_null() || high.is_null() {
    return Evaluated::Value(Cow::Owned(Value::Null));
}

다음 테스트 하나만 실행해도 조건문과 return이 있는 줄은 모두 실행됩니다.

SELECT NULL BETWEEN 1 AND 3;

||는 앞 조건만으로 결과가 정해지면 뒤 조건을 실행하지 않는 short-circuit evaluation을 사용합니다. 위 입력에서는 target.is_null()이 true이므로 low.is_null()과 high.is_null()은 실행되지 않습니다.

이 코드를 확인하려면 NULL이 놓이는 위치와 NULL이 없는 경우를 나누어 볼 수 있습니다.

입력 확인하는 조건
NULL BETWEEN 1 AND 3 target.is_null()
1 BETWEEN NULL AND 3 low.is_null()
1 BETWEEN 1 AND NULL high.is_null()
1 BETWEEN 0 AND 3 세 조건이 모두 false인 경우

실제 GlueSQL의 between fixture는 target, lower bound, upper bound가 각각 NULL인 경우와 NULL이 없는 경우를 나누어 확인합니다. line coverage가 이미 채워졌더라도 테스트할 의미가 있는 경우는 더 남아 있습니다.

line, region, branch coverage

line coverage 외에도 같은 실행 결과를 더 세밀하게 보는 지표가 있습니다.

지표 확인하는 것
line coverage 해당 코드 줄이 한 번 이상 실행됐는가
region coverage 한 줄 안에서도 나뉠 수 있는 개별 코드 영역이 실행됐는가
branch coverage 각 조건의 true와 false 결과를 모두 거쳤는가

region coverage는 한 줄에 여러 표현식이 있을 때 line coverage보다 세밀한 정보를 줄 수 있습니다. branch coverage는 조건식의 각 결과를 확인하므로 앞의 || 예시처럼 일부 조건이 실행되지 않은 경우를 찾는 데 도움이 됩니다.

다만 더 세밀한 지표도 테스트의 완전함을 보장하지는 않습니다.

모든 줄을 실행해도 panic은 남을 수 있다

다음 함수와 테스트를 생각해봅니다.

fn first(values: &[i32]) -> i32 {
    values[0]
}

assert_eq!(first(&[10]), 10);

이 테스트를 실행하면 함수의 모든 줄이 실행되므로 line coverage는 100%입니다. 코드 안에 명시적인 분기도 없어서 region coverage나 branch coverage에서 추가로 드러날 정보도 거의 없습니다.

하지만 first(&[])를 호출하면 index out of bounds로 panic이 발생합니다. coverage는 테스트가 어떤 코드를 실행했는지 보여줄 뿐, 가능한 입력의 범위를 자동으로 탐색하거나 코드가 안전한지 판단하지 않습니다.

coverage를 보완하는 테스트

fuzz testing은 다양한 입력을 자동으로 만들어 crash나 panic, 예상하지 못한 상태를 찾는 데 도움을 줍니다.

mutation testing은 코드의 연산자나 조건을 일부러 바꾼 뒤 기존 테스트가 그 변경을 발견하는지 확인합니다. Rust에서는 cargo-mutants를 사용할 수 있습니다. 코드가 실행됐는지를 넘어 테스트의 assertion이 동작 변화를 실제로 감지하는지 살펴보는 방법입니다.

이 방법들은 line coverage를 대체하기보다 서로 다른 빈틈을 확인합니다. 프로젝트 전체에 반복 적용하는 비용과 결과를 해석하는 방식도 서로 다릅니다.

GlueSQL이 line coverage를 기준으로 삼는 이유

GlueSQL이 line coverage를 대표적인 기준으로 사용하는 이유는 이 수치가 테스트 품질을 완전히 설명하기 때문이 아닙니다.

  • 넓은 workspace 전체에서 반복해 측정하기 쉽습니다.
  • 하나의 비율로 이전 결과와 Pull Request의 변화를 비교할 수 있습니다.
  • 테스트되지 않은 줄을 파일과 위치 단위로 확인할 수 있습니다.
  • CI와 로컬에서 비교적 같은 방식으로 재현할 수 있습니다.
  • 더 많은 실행 시간과 별도의 분석이 필요한 테스트 기법보다 지속적으로 관리하기 쉽습니다.

2026년 7월 19일 현재 GlueSQL의 coverage workflow는 Rust의 LLVM coverage instrumentation 결과를 LCOV로 만들어 Codecov와 Coveralls에 전달합니다. 측정 도구를 cargo-llvm-cov로 바꾸는 작업도 Pull Request #1938에서 진행하고 있습니다.

도구가 바뀌더라도 line coverage를 읽는 기준은 같습니다. 이 숫자는 테스트 품질의 합격 점수가 아니라, 테스트되지 않은 코드가 늘어나지 않는지 지속적으로 살펴보기 위한 정량적인 기준입니다.

coverage는 테스트가 어디를 실행했는지는 알려주지만, 어떤 입력을 빠뜨렸는지와 그 동작이 안전한지는 보장하지 않습니다.
