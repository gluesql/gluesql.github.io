GlueSQL의 planner는 어떤 일을 할까요

Planner라는 이름을 처음 접하면 쿼리를 더 빠르게 실행할 방법을 고르는 옵티마이저(optimizer)를 먼저 떠올릴 수 있습니다. 하지만 GlueSQL의 플래너는 그보다 넓은 일을 맡고 있습니다.

스키마와 스토리지가 제공하는 기능을 확인하고, 기본 키(primary key)와 인덱스를 이용할 위치를 찾습니다. JOIN의 실행 방법을 선택하고, 집계와 표현식을 실행 계층(executor)이 사용할 수 있도록 준비합니다. 스키마를 미리 정의하지 않은 테이블도 같은 실행 계층에서 처리할 수 있도록 쿼리를 변환합니다.

GlueSQL의 플래너는 현재도 역할과 내부 구조를 계속 다듬고 있습니다. 지금 코드의 구성과 처리 순서를 완성된 설계처럼 설명하면 빠르게 낡을 수 있고, 지향점만 설명하면 아직 구현되지 않은 기능을 현재 모습처럼 보이게 할 수 있습니다.

이번 글에서는 구체적인 내부 구조보다 GlueSQL의 플래너가 맡아야 하는 역할을 중심으로 살펴봅니다. 현재 구현을 설명할 때는 지금 가능한 일과 앞으로 발전시킬 영역을 구분합니다.

SQL과 실행 사이에 플래너가 있습니다

GlueSQL에서 SQL 한 문장은 다음 단계를 거쳐 실행됩니다.

SQL
→ parse
→ translate
→ planner
→ executor
→ storage

파서는 SQL 문법을 읽습니다. translate 모듈은 외부 파서의 AST를 GlueSQL이 지원하는 내부 AST로 옮깁니다.

Translate 단계에서는 쿼리가 참조하는 테이블의 스키마와 스토리지가 제공하는 기능을 아직 확인하지 않습니다. 같은 SQL이라도 어떤 컬럼이 기본 키인지, 사용할 수 있는 인덱스가 있는지, 테이블에 스키마가 정의되어 있는지에 따라 실행 준비가 달라질 수 있습니다.

현재 GlueSQL은 translate가 만든 내부 AST를 StatementPlan으로 옮긴 뒤 스토리지의 Planner에 전달합니다. Rust Query Builder로 만든 쿼리도 파싱과 translate를 거치지 않을 뿐, 같은 플래너와 실행 계층으로 이어집니다.

플래너는 쿼리에 스키마와 스토리지 정보를 결합해 실행 계층에 필요한 결정을 실행 계획(plan)에 남깁니다. 실행 계층은 그 결정을 이용해 스토리지에서 실제 데이터를 읽고 쿼리를 실행합니다.

현재 각 단계에서 사용하는 정보가 다릅니다

  • Translate — SQL 문법과 GlueSQL이 지원하는 AST를 다룹니다. 실제 테이블의 스키마는 아직 모릅니다.
  • Planner — 쿼리의 AST와 리터럴, 파라미터에 스키마와 인덱스 메타데이터를 결합합니다.
  • Executor — 실행 계획에 기록된 결정에 따라 스토리지에서 실제 행을 읽고 연산합니다.

단계가 내려갈수록 판단에 사용할 수 있는 정보가 늘어납니다. Translate가 SQL의 구조를 표현하면, 플래너는 실제 스키마와 스토리지의 기능을 바탕으로 실행 전에 알 수 있는 내용을 실행 계획에 남깁니다. 실행 계층에 이르러서야 실제 행을 읽습니다.

현재 GlueSQL의 플래너는 스키마 메타데이터를 이용해 규칙 기반으로 실행 계획을 만듭니다. 실제 데이터의 양과 분포를 바탕으로 실행 비용을 비교하는 기능은 아직 구현되어 있지 않습니다. 이는 플래너 역할의 한계라기보다, 앞으로 플래너를 발전시키며 다룰 수 있는 영역입니다.

플래너는 실행 전에 결정을 남깁니다

GlueSQL의 플래너가 하는 일은 한 가지 기능으로 설명하기 어렵습니다. 현재 구현에서는 다음과 같은 판단이 서로 연결되어 있습니다.

  • 쿼리에 실제 스키마와 스토리지의 기능을 연결합니다.
  • 기본 키 조회와 인덱스 스캔, JOIN의 실행 방법을 선택합니다.
  • 집계와 표현식을 실행 계층이 정해진 순서로 평가할 수 있도록 준비합니다.
  • GlueSQL이 지원하는 여러 형태의 테이블을 공통 실행 계층이 처리할 수 있는 표현으로 바꿉니다.

이 역할들을 현재의 특정 함수나 처리 단계와 일대일로 대응시킬 필요는 없습니다. 세부 책임과 실행 순서는 계속 정리되고 있지만, 실행 계층이 SQL의 의미를 다시 해석하거나 실행 방법을 그때마다 선택하지 않도록 미리 결정을 남긴다는 목적은 같습니다.

SQL에는 실행 방법이 적혀 있지 않습니다

다음 테이블과 쿼리를 생각해보겠습니다.

CREATE TABLE Player (
    id INTEGER PRIMARY KEY,
    active BOOLEAN
);

SELECT *
FROM Player
WHERE id = 1 AND active = TRUE;

SQL에는 Player에서 어떤 결과가 필요한지는 적혀 있지만, 행을 어떻게 가져올지는 적혀 있지 않습니다.

플래너가 기본 키를 확인하기 전의 상태를 간단히 표현하면 다음과 같습니다.

Table: Player
Access path: 없음
Selection: id = 1 AND active = TRUE

플래너는 스토리지에서 가져온 스키마를 통해 id가 기본 키라는 사실을 확인합니다. id = 1에서 값 1은 행을 읽기 전에 알 수 있으므로, 이 조건을 기본 키 조회에 사용할 수 있습니다.

실행 계획을 만든 뒤의 상태는 다음처럼 바뀝니다.

Table: Player
Access path: PrimaryKey(1)
Selection: active = TRUE

실행 계층은 이제 테이블의 모든 행을 scan_data로 읽지 않고, fetch_data를 이용해 키가 1인 행을 찾습니다. 접근 경로(access path)에 반영된 id = 1은 selection에서 제거하고, 가져온 행에서 계속 확인해야 하는 active = TRUE만 남깁니다.

이 과정은 성능만의 문제가 아닙니다. 접근 경로로 옮긴 조건을 selection에서 잘못 제거하거나 다른 테이블의 조건을 사용하면 쿼리 결과 자체가 달라질 수 있습니다.

플래너가 실행 방법을 바꿀 때는 SQL의 의미가 그대로 유지되는지도 함께 보장해야 합니다.

최적화가 아닌 실행 준비도 있습니다

기본 키 조회만 보면 플래너를 옵티마이저와 같은 의미로 생각하기 쉽습니다. 집계 계획은 플래너가 실행 전에 필요한 구조를 준비하기도 한다는 점을 보여줍니다.

SELECT team_id, COUNT(*) AS player_count
FROM Player
GROUP BY team_id
HAVING COUNT(*) >= 2
ORDER BY COUNT(*) DESC;

이 쿼리에서 COUNT(*) 결과는 출력과 HAVING, ORDER BY에서 사용됩니다. 실행 계층이 이 표현식들을 올바른 순서로 평가하려면, 어떤 집계를 계산하고 그 결과를 어디에서 사용할지 미리 정해야 합니다.

현재 GlueSQL의 플래너는 계산할 집계 표현식을 수집하고, 같은 결과를 사용하는 위치를 aggregate slot에 연결합니다. 실행 계층은 집계를 계산한 뒤 그 결과를 HAVING, 출력과 정렬 과정에서 사용할 수 있습니다.

Aggregate slot을 나타내는 내부 구조는 앞으로 달라질 수 있습니다. 하지만 쿼리를 실행하기 전에 어떤 계산이 필요하고 그 결과를 어디에서 사용할지 정리하는 일은 플래너가 맡아야 할 역할로 남습니다.

GlueSQL에서는 스키마가 없는 테이블도 함께 다룹니다

GlueSQL은 컬럼을 미리 정의한 테이블뿐 아니라 스키마를 지정하지 않은 테이블도 지원합니다. 스키마리스(schemaless) 테이블은 행 전체를 하나의 맵 값처럼 다룹니다.

CREATE TABLE Player;

SELECT name
FROM Player;

스키마가 있는 테이블에서는 name을 미리 정의된 컬럼으로 읽을 수 있습니다. 스키마리스 테이블에는 같은 컬럼 정의가 없으므로, 현재 GlueSQL은 행 전체를 담은 _doc에서 필드를 읽는 표현식으로 쿼리를 바꿉니다.

개념적으로는 다음과 같습니다.

SELECT _doc['name'] AS name
FROM Player;

이 작업은 더 빠른 알고리즘을 선택하는 최적화가 아닙니다. 테이블에 스키마가 있는지에 따라 사용자가 작성한 표현식을 실행 가능한 형태로 바꾸는 계획 과정입니다.

참조를 나타내는 구체적인 방식과 각 단계의 책임도 계속 정리하고 있습니다. 다만 스키마가 있는 테이블과 스키마리스 테이블을 같은 SQL 인터페이스와 실행 계층으로 연결하려면, 실행 전에 테이블의 정보를 확인하고 적절한 표현으로 바꾸는 과정이 필요하다는 점은 변하지 않습니다.

스토리지도 실행 계획을 만드는 데 참여합니다

GlueSQL에서는 Planner도 스토리지가 구현하는 trait입니다. 대부분의 스토리지는 공통 계획 과정을 사용하고, 필요한 경우 스토리지에 맞는 계획을 추가할 수 있습니다.

현재 SledStorage의 Planner는 비클러스터형 인덱스(non-clustered index)를 사용할 수 있는 조건을 찾습니다. 사용할 수 있는 인덱스가 있다면 테이블의 접근 경로에 인덱스 스캔을 기록하고, 실행 계층은 일반적인 scan_data 대신 scan_indexed_data를 사용합니다.

이 구조는 Store traits가 단순히 행을 읽고 쓰는 API에 머물지 않는 이유이기도 합니다.

여러 스토리지가 공통 플래너와 실행 계층을 재사용하면서도 자신이 제공하는 조회 방법을 실행 계획에 반영할 수 있습니다. 새로운 스토리지를 연결할 때 SQL의 모든 실행 과정을 다시 만드는 대신 공통 계획으로 시작하고, 필요한 기능이 있다면 스토리지에 맞는 계획을 더할 수 있습니다.

여러 종류의 스토리지를 같은 SQL 인터페이스로 연결하려는 GlueSQL에서는 공통 계획과 스토리지별 계획의 경계를 나누는 것도 중요합니다.

현재 구조와 지향점을 함께 봅니다

GlueSQL의 플래너는 처음부터 완성된 옵티마이저 구조를 한 번에 만든 것이 아닙니다. 인덱스와 hash join, 스키마리스 처리와 집계 바인딩처럼 실제 기능에 필요한 결정을 하나씩 플래너로 옮겨왔습니다.

2026년에는 StatementPlan을 도입한 변경을 통해 SQL의 의미를 표현하는 AST와, 계획 및 실행에 필요한 구조를 분리하기 시작했습니다.

현재 StatementPlan에는 여전히 SELECT, FROM, WHERE, ORDER BY처럼 SQL 문법과 가까운 형태가 많이 남아 있습니다. 동시에 테이블 접근 경로와 JOIN 알고리즘, aggregate slot처럼 구체적인 실행 결정도 함께 담습니다. 논리 계획(logical plan)과 물리 실행 계획(physical execution plan)이 완전히 나뉜 구조라기보다 두 역할이 함께 발전하는 과정에 있습니다.

컬럼 참조가 어느 relation과 컬럼을 가리키는지 확정하는 일과 타입 변환(type coercion)의 일부도 아직 실행 계층에 남아 있습니다. 통계와 비용을 이용해 여러 실행 방법을 비교하거나 JOIN 순서를 바꾸는 비용 기반 최적화(cost-based optimization)도 현재 플래너에는 구현되어 있지 않습니다.

GlueSQL은 이 상태를 최종 구조로 두기보다 다음 방향으로 플래너를 계속 정리하고 있습니다.

  • 문법에 가까운 표현을 실행 계층이 사용할 수 있는 참조와 연산자로 바꿉니다.
  • SQL 절을 나열한 형태에서 실제 실행 순서가 드러나는 실행 계획 구조로 옮깁니다.
  • 플래너가 내린 결정과 실행 계층이 수행할 일을 더 명확히 나눕니다.
  • 스토리지가 제공하는 기능과 앞으로 활용할 비용 정보를 실행 계획에 반영할 수 있게 합니다.

이 변화는 현재 코드에 단계적으로 반영되고 있습니다. 따라서 지금 보이는 함수 이름과 처리 순서를 플래너의 최종 구조로 이해하기보다, SQL을 실행 가능한 계획으로 바꾸기 위해 책임을 나누어가는 과정으로 보는 편이 정확합니다.

더 살펴볼 수 있는 질문들

이번 글은 플래너의 각 기능을 모두 설명하는 문서가 아니라, 이후 내용을 읽기 위한 개요(overview)입니다. 앞으로 다룰 글의 제목과 순서를 미리 정하기보다, 플래너를 이해하기 위해 다음과 같은 질문들을 생각해볼 수 있습니다.

  • SQL은 무엇을 의미할까요?
    이름 참조 연결(identifier binding)과 쿼리 범위(query scope), 타입 계획(type planning)처럼 실행 계층이 행을 읽기 전에 확정해야 할 의미가 있습니다.

  • 같은 의미를 어떻게 실행할까요?
    테이블 스캔과 접근 경로, JOIN 알고리즘과 스토리지의 기능처럼 같은 결과를 만드는 여러 실행 방법을 비교할 수 있습니다.

  • 결정을 어떤 실행 계획으로 남길까요?
    AST와 논리 계획, 물리 실행 계획과 연산자 파이프라인(operator pipeline)처럼 플래너의 판단을 실행 계층이 사용할 수 있는 구조를 생각해볼 수 있습니다.

  • 여러 스토리지를 위해 무엇이 달라져야 할까요?
    공통 플래너와 스토리지별 계획, 연산을 스토리지로 내리는 pushdown과 비용처럼 하나의 SQL 인터페이스를 유지하면서도 각 스토리지의 특성을 활용하는 방법을 살펴볼 수 있습니다.

GlueSQL에서 플래너는 SQL 문장을 스토리지에서 실행할 수 있는 결정으로 바꾸는 계층입니다.

스키마와 스토리지 정보를 결합하고, 실행 방법을 선택하고, 실행 전에 필요한 구조를 준비하는 일은 이 한 경계 안에서 서로 연결되어 있습니다. 플래너의 역할을 이해하는 것은 쿼리가 파서와 translate를 지난 뒤 실제 데이터에 도달하기까지 GlueSQL이 어떤 판단을 하는지 이해하는 일입니다.
