GlueSQL에는 왜 translate 모듈이 있을까요

GlueSQL에서 SQL 한 문장을 실행하면 내부에서는 다음 단계를 거칩니다.

SQL
→ sqlparser-rs AST
→ GlueSQL AST
→ StatementPlan
→ 실행

SQL을 읽은 parser가 이미 AST를 만들었는데, GlueSQL은 왜 이를 다시 자신의 AST로 옮길까요? 대부분의 데이터베이스 코드에서 translate라는 이름의 모듈을 따로 접할 일도 많지 않습니다.

이 질문에 답하려면 먼저 GlueSQL이 SQL parser를 직접 만들지 않은 이유와, 그렇다고 특정 데이터베이스의 호환 구현을 선택하지도 않은 이유를 함께 살펴봐야 합니다. translate 모듈은 이 두 선택 사이에 만들어진 경계입니다.

SQL parser를 직접 만들지 않았습니다

GlueSQL은 SQL 문장을 읽는 데 sqlparser-rs를 사용합니다. sqlparser-rs는 SQL 문자열을 token으로 나누고 문법에 따라 해석한 뒤, statement와 expression으로 구성된 AST를 반환하는 Rust library입니다.

SQL parser를 만드는 일은 SELECT, FROM, WHERE 같은 keyword를 구분하는 데서 끝나지 않습니다. 연산자 우선순위와 괄호, 중첩 query, quoted identifier, 여러 종류의 literal과 DDL을 함께 처리해야 합니다. 올바른 문장은 빠짐없이 읽고 잘못된 문장은 적절한 위치에서 거절해야 하며, SQL 문법이 확장될 때마다 parser와 테스트도 계속 관리해야 합니다.

이미 검증되고 꾸준히 관리되는 parser를 사용하면 이 작업을 처음부터 반복하지 않아도 됩니다. GlueSQL은 parsing보다 storage, planner와 executor처럼 프로젝트에서 직접 해결하려는 문제에 더 많은 시간을 사용할 수 있습니다. sqlparser-rs가 새로운 문법을 지원하면 GlueSQL도 tokenizer와 parser부터 다시 구현하지 않고, 필요한 기능을 내부 AST와 실행 계층에 연결하는 작업부터 시작할 수 있습니다.

하지만 외부 parser를 사용하면 제약도 생깁니다.

  • sqlparser-rs의 AST에는 GlueSQL이 지원하지 않는 statement와 option도 포함됩니다.
  • parser가 문법적으로 읽은 SQL을 GlueSQL이 반드시 실행할 수 있는 것은 아닙니다.
  • library를 upgrade하며 외부 AST의 구조가 바뀌면 이를 사용하는 코드도 수정해야 합니다.
  • GlueSQL만의 문법이 필요해져도 parser가 그 문장을 읽지 못하면 내부 기능으로 연결할 수 없습니다.

따라서 parser를 재사용한다는 선택만으로 GlueSQL이 지원할 SQL의 범위와 동작까지 정해지는 것은 아닙니다.

parser를 재사용해도 SQL의 의미까지 따르는 것은 아닙니다

새로운 데이터베이스가 사용자에게 빠르게 다가가려면 PostgreSQL, MySQL이나 SQLite와의 호환을 목표로 삼는 것도 좋은 전략입니다. 사용자는 이미 알고 있는 syntax와 도구를 활용할 수 있고, 새로운 사용 방법을 익히는 시간도 줄어듭니다.

개발 과정에서도 이미 동작하는 데이터베이스를 기준으로 삼으면 편한 점이 있습니다. 구현해야 할 전체 범위가 작다는 뜻은 아니지만, 개별 기능의 기대 동작은 기존 구현과 문서에서 확인할 수 있습니다. 기능마다 어떤 결과가 적절한지 처음부터 기획하는 시간을 줄이고, 같은 결과가 나오도록 구현하고 검증하는 데 집중할 수 있습니다.

GlueSQL은 특정 데이터베이스와의 호환을 프로젝트의 목표로 두지 않았습니다. 익숙한 SQL interface는 활용하되, 어떤 syntax와 동작을 지원할지는 GlueSQL에서 직접 기획하는 쪽을 선택했습니다.

이 선택에는 외부와 내부의 시간이 모두 필요합니다. 사용자는 익숙한 데이터베이스와 같은 동작을 바로 기대하는 대신 GlueSQL의 지원 범위를 확인해야 합니다. 개발할 때도 기존 specification을 그대로 따라가기보다 어떤 동작이 적절한지, 오류와 경계 조건은 무엇인지, 어느 계층에서 처리할지 직접 정하고 문서와 테스트로 남겨야 합니다.

대신 이러한 설계 자유는 서로 다른 storage를 하나의 SQL interface로 연결할 때 유용합니다. 메모리와 key-value storage, 파일과 remote API, schema가 있는 storage와 schemaless storage는 지원할 수 있는 기능과 데이터를 다루는 방법이 서로 다릅니다. 특정 데이터베이스의 기존 동작을 모두 재현하는 대신 각 차이를 어느 계층에서 처리하고, 어떤 기능을 공통으로 제공할지 GlueSQL의 기준에서 결정할 수 있습니다.

개발 과정에서 직접 결정할 여지가 남는다는 점도 중요합니다. 새로운 SQL 기능을 추가하며 기존 구현과 표준을 살펴보고, GlueSQL에 적합한 동작을 기획하고, parser부터 executor까지 어떻게 연결되는지 하나씩 알아갈 수 있습니다. 기능마다 기획과 검토가 필요하지만, 그 과정을 통해 데이터베이스를 이해해 가는 것 자체도 GlueSQL을 개발하는 동기입니다.

그렇다고 모든 작업을 처음부터 직접 반복하려는 것은 아닙니다. SQL을 parsing하는 작업에는 검증된 sqlparser-rs를 활용하고, GlueSQL에서 어떤 의미로 사용할지는 직접 결정합니다. Parser를 만드는 비용은 재사용으로 줄이되 SQL의 의미를 정하는 부분은 내부에서 소유하는 선택입니다.

두 선택 사이에 translate가 있습니다

일반적인 데이터베이스에도 parser가 만든 구조를 분석하고 실행 계획으로 바꾸는 과정은 있습니다. 다만 자체 parser가 데이터베이스의 내부 구조에 맞는 AST를 바로 생성한다면, 외부 AST를 다시 옮기는 translate가 독립된 모듈로 드러날 필요는 적습니다.

GlueSQL은 검증된 범용 parser를 사용하면서도, 특정 데이터베이스의 SQL 의미와 실행 구조를 그대로 따르지는 않습니다. 이 두 선택 사이에는 자연스럽게 간격이 생깁니다.

sqlparser-rs가 읽을 수 있는 SQL
              ↓ translate
GlueSQL이 지원하고 의미를 부여한 SQL

translate는 sqlparser-rs의 Statement를 GlueSQL의 Statement로 변환합니다. 이 과정에서 단순히 비슷한 field를 복사하는 것이 아니라, GlueSQL이 지원할 범위를 확인하고 이후 단계가 사용할 수 있는 일관된 내부 표현을 만듭니다.

문법적으로 유효한 SQL과 지원하는 SQL을 구분합니다

sqlparser-rs는 여러 SQL dialect의 넓은 문법을 다루므로 GlueSQL이 아직 실행하지 않는 구문도 AST로 만들 수 있습니다. 예를 들어 현재 GlueSQL은 WITH, FETCH, query lock과 SELECT INTO 등을 translate 단계에서 거절합니다.

이 구분 덕분에 오류가 발생한 단계도 분명해집니다.

  • Parser error: SQL 문법 자체를 읽을 수 없습니다.
  • Translate error: 문법은 읽었지만 GlueSQL이 지원하지 않는 기능입니다.
  • Plan error: table과 column, schema나 storage를 확인하는 과정에서 실행할 수 없습니다.
  • Execute 또는 Evaluate error: 준비된 계획을 실제로 실행하는 과정에서 문제가 발생합니다.

문법적으로 유효하다는 사실과 GlueSQL에서 지원한다는 사실을 분리하면, executor가 외부 parser에 존재하는 모든 statement와 option을 알 필요도 없어집니다. translate_query는 query가 GlueSQL AST로 넘어가기 전에 이 경계를 확인합니다.

내부에서 일관되게 다룰 형태로 바꿉니다

지원 여부를 확인한 뒤에는 같은 의미를 내부에서 일관된 형태로 다룰 수 있도록 정리합니다. SELECT 1은 이 역할을 잘 보여주는 예입니다.

SELECT 1;

이 query에는 FROM이 없습니다. 사용자 입장에서는 별도의 table 없이 값 하나를 조회하는 자연스러운 SQL이지만, 실행 계층에서 FROM이 있는 query와 없는 query를 매번 나누어 처리하면 이후 로직에 예외가 늘어납니다.

GlueSQL의 translate는 FROM이 없을 때 크기가 1인 Series를 입력으로 추가합니다.

SELECT 1
→ 한 행을 가진 Series에서 1을 선택

사용자가 작성하는 SQL은 그대로 유지하면서 내부에서는 모든 SELECT가 입력을 가진다는 같은 전제 아래 처리할 수 있습니다. translate_select가 단순한 AST 복사보다 normalization도 함께 수행하는 이유입니다.

데이터 타입에서도 같은 작업을 찾을 수 있습니다. translate_data_type는 INT, INTEGER, INT64를 GlueSQL의 하나의 DataType::Int로 연결합니다. 반대로 parser가 custom type으로 읽은 MAP, LIST, POINT, INET에는 GlueSQL의 내부 타입을 부여합니다.

Parameter binding도 translate를 통과합니다. $1 같은 placeholder를 SQL 문자열에 다시 끼워 넣는 대신, 전달받은 Rust 값을 GlueSQL의 type을 가진 Value로 변환해 expression에 연결합니다. 외부 SQL 표현을 내부에서 사용할 수 있는 명확한 값과 enum으로 바꾸는 것도 translate의 역할입니다.

planner가 할 일은 남겨 둡니다

Translate가 GlueSQL의 의미를 결정한다고 해서 table과 storage에 관한 모든 판단까지 담당하는 것은 아닙니다. 이 단계에서는 table이나 column이 실제로 존재하는지, storage가 어떤 기능을 제공하는지 알지 못합니다.

Translate 이후의 Planner는 schema와 storage를 확인하며 다음 작업을 진행합니다.

  • expression에서 사용하는 table과 column을 검증합니다.
  • schemaless storage에서 실행할 수 있도록 statement를 계획합니다.
  • primary key와 index를 사용할 위치를 정합니다.
  • join과 aggregate를 실행할 구조를 준비합니다.

각 계층의 경계를 정리하면 다음과 같습니다.

parser
SQL 문법을 읽어 외부 AST를 생성

translate
GlueSQL이 지원할 SQL을 내부 AST로 변환

planner
schema와 storage를 고려해 StatementPlan을 구성

executor
준비된 계획을 실제로 실행

Translate를 “실행 가능한 형태를 만드는 곳”이라고만 설명하면 planner의 역할과 섞일 수 있습니다. Storage를 확인하기 전에 GlueSQL이 이해하는 언어로 낮추는 곳이라고 보는 편이 더 정확합니다.

외부 parser와 실행 계층을 분리해 왔습니다

GlueSQL의 초기 구조에서 실행 계층은 sqlparser-rs의 AST와 더 가까이 연결되어 있었습니다. 2021년 5월 Add new AST for execution layer commit에서 GlueSQL의 AST와 이를 만드는 translate 모듈이 추가되었습니다. 다음 날 Replace sqlparser-rs AST to new execution layer AST! commit을 통해 executor와 storage가 외부 parser AST 대신 새로운 내부 AST를 사용하기 시작했습니다.

이 경계가 생기면서 sqlparser-rs의 AST가 변경되어도 영향을 parser와 translate 주변에 모을 수 있게 되었습니다. Executor는 여러 dialect를 위해 존재하는 외부 AST의 모든 variant를 따라가지 않고, GlueSQL이 선택한 내부 표현을 기준으로 발전할 수 있습니다.

이후 Query Builder는 SQL 문자열을 만들었다가 다시 parsing하지 않고 GlueSQL의 구조를 직접 구성하는 또 다른 입구가 되었습니다. 2026년에는 StatementPlan을 도입한 변경을 통해 SQL의 의미를 표현하는 AST와 planning 및 execution에 필요한 구조도 분리하기 시작했습니다.

처음에는 외부 parser AST와 실행 계층을 나누기 위해 만들어진 경계가, 지금은 parser와 Query Builder, planner와 executor가 각자의 역할을 유지할 수 있는 기반이 된 셈입니다.

기존 SQL 문법으로 표현할 수 없다면

SQL은 공통된 형태를 가지고 있지만 PostgreSQL과 MySQL, SQLite처럼 데이터베이스마다 읽을 수 있는 문법에는 차이가 있습니다. sqlparser-rs에서는 이러한 문법의 차이를 dialect로 구분합니다.

GlueSQL은 현재 PostgreSqlDialect를 사용해 SQL을 parsing합니다. PostgreSQL 호환을 목표로 선택한 정책이라기보다, 현재 필요한 SQL을 읽을 수 있는 실용적인 parser 설정입니다.

지금까지 GlueSQL의 기능은 sqlparser-rs가 제공하는 기존 SQL 문법과 AST 안에서 대부분 표현할 수 있었습니다. MAP과 LIST처럼 GlueSQL에 특화된 의미도 parser가 읽을 수 있는 구조라면 translate에서 내부 타입으로 연결할 수 있습니다. 별도의 GlueSQL dialect가 아직 필요하지 않았던 이유입니다.

앞으로 schemaless 데이터를 더 자연스럽게 다루기 위해 기존 parser가 표현하기 어려운 syntax가 필요해진다면, sqlparser-rs에 GlueSqlDialect를 추가하는 것도 선택지가 될 수 있습니다.

다만 별도 dialect를 만드는 것 자체가 현재의 목표는 아닙니다. 기존 문법으로 충분한 동안에는 이미 검증된 parser를 활용하고, 실제로 새로운 문법이 필요한 시점에 확장 범위와 유지 비용을 함께 판단할 수 있습니다.

Dialect가 추가되더라도 parser가 읽은 syntax를 GlueSQL의 타입과 expression으로 바꾸고, 지원 범위를 정리하는 경계는 여전히 필요합니다.

sqlparser-rs가 SQL을 읽는다면, translate는 그 SQL이 GlueSQL에서 무엇을 의미하는지 결정합니다.

GlueSQL의 translate는 단순한 자료 구조 변환 코드가 아닙니다. SQL parser를 직접 개발하고 유지하는 비용은 줄이면서도 특정 데이터베이스의 문법과 내부 구조에는 종속되지 않기 위해 마련한 모듈입니다.
