2026년 8월 24일 · 오픈소스 기여

GlueSQL에서 기여할 문제를 찾고 코드를 읽는 방법

이전 글에서는 오픈소스에 기여할 일이 왜 계속 생기는지 살펴봤습니다. 프로젝트에 필요한 일이 없어서 Issue가 남아 있는 것이 아니라, 필요한 일이 생기는 속도가 사람이 처리할 수 있는 속도보다 빠르기 때문에 기여 기회가 계속 만들어진다는 이야기였습니다.

그렇다면 실제로는 어디에서 시작하면 좋을까요. GitHub의 Issue 목록에는 문서 한 줄을 고치는 작업부터 planner의 판단을 바꾸는 작업까지 서로 다른 크기의 문제가 함께 있습니다. 제목만 읽어서는 자신이 어디까지 할 수 있는지, 어떤 코드를 먼저 봐야 하는지 알기 어려울 수 있습니다.

이 글에서는 2026년 7월부터 8월 24일까지 GlueSQL에서 실제로 이어진 Issue와 Pull Request를 살펴봅니다. 모든 작업을 나열하기보다, 기여거리를 발견하고 코드의 위치를 좁히는 데 다시 사용할 수 있는 방법을 중심으로 사례를 골랐습니다.

처음부터 끝까지 순서대로 읽을 필요는 없습니다. 지금 관심 있는 출발점과 가까운 사례를 먼저 보고, 더 궁금한 구현은 연결된 Issue와 Pull Request에서 이어서 살펴봐도 됩니다.

어디에서 시작할까 대표 사례 살펴볼 지점
사용자가 하려는 일 OPFS browser storage library 밖에서 직접 구성하는 부분
실제 실행 결과 CREATE INDEX, foreign key, migration 입력의 의미와 실패 뒤 상태의 보존
새로운 제안 tracing observability 프로젝트에 아직 없던 접근
기존 Issue와 review table factor, JOIN planner 선행 작업과 책임 경계
테스트와 이웃 코드 IN subquery, aggregate, translate 비슷한 처리 경로 사이의 차이

먼저 기억해 둘 것은 프로젝트 전체를 이해한 뒤 시작하는 순서가 아니라는 점입니다.

재현 가능한 작은 현상을 찾고, 가장 가까운 테스트를 읽고, 동작이 달라지는 첫 번째 코드 지점을 찾습니다.

이 세 가지가 정리되면 아직 해결 방법을 모두 알지 못하더라도 다음 질문을 구체적으로 만들 수 있습니다.

Issue는 구현 지시서보다 인수인계 문서에 가깝습니다

좋은 Issue에는 완성된 설계가 없어도 됩니다. 다음 사람이 같은 현상을 확인하고 탐색을 이어갈 수 있는 단서가 있으면 됩니다.

  • 어떤 입력이나 SQL에서 문제가 발생하는지
  • 현재 동작과 기대 동작이 어떻게 다른지
  • 비슷한 처리를 하는 코드나 테스트가 어디에 있는지
  • 이번 작업에서 다루지 않아도 되는 범위가 무엇인지

Issue를 등록한 사람과 Pull Request를 작성한 사람이 같을 수도 있고 다를 수도 있습니다. 문제를 관찰하고 재현 범위를 정리하는 일과, 현재 코드에 맞는 구현을 완성하는 일은 각각 독립적인 기여입니다.

작은 SQL에서 한 파일의 수정까지

ORDER BY schema dependency 누락 · Issue #1906 · @panarch / PR #1982 · @seosangwon

다음 query에서 Bar는 ORDER BY 안에서만 등장합니다.

SELECT *
FROM Foo
ORDER BY (SELECT id FROM Bar LIMIT 1);

GlueSQL은 query를 실행하기 전에 필요한 table schema를 모읍니다. 당시에는 query body와 LIMIT, OFFSET은 확인했지만 ORDER BY 안의 expression은 순회하지 않아 Bar가 dependency에서 빠졌습니다.

Issue는 빠진 위치와 다른 expression에서 이미 쓰던 scanner를 함께 알려줬습니다. PR은 그 scanner를 ORDER BY에도 연결하고, scalar subquery가 하나일 때와 여러 정렬 expression이 있을 때를 한 파일에서 검증했습니다. planner 전체를 새로 이해하기보다 짧은 재현에서 빠진 순회 하나를 찾은 사례입니다.

문제와 작업 범위를 함께 남기기

Parquet row streaming · Issue #1967 · @jminlee-ur / PR #1968 · @dgg1dbg

ParquetStorage::scan_data는 iterator를 반환했지만, 당시 구현은 Parquet의 모든 row를 먼저 모은 뒤 iterator를 만들었습니다. interface는 필요할 때 읽는 것처럼 보였지만 실제로는 전체 table을 먼저 읽었습니다.

Issue는 row streaming에 집중하고 projection pushdown, row-group 통계, Arrow execution, mutation rewrite는 첫 작업에서 제외했습니다. 구현 PR도 storage interface나 planner를 바꾸지 않았습니다.

PR에 기록된 250,000 row benchmark에서 LIMIT 10은 71.0 ms에서 1.11 ms로 줄었지만 COUNT(*)는 83.9 ms에서 74.9 ms로 바뀌었습니다. 모든 query가 같은 폭으로 빨라진 것이 아니라, iterator가 일찍 멈출 수 있는 query에서 변화가 크게 나타난 것입니다.

이처럼 성능 작업은 “더 빠르게”만 적기보다 interface와 실제 동작의 차이, early stop과 full scan의 측정 결과, 첫 PR에서 바꾸지 않을 범위를 함께 남기면 이어가기 쉽습니다.

기여거리를 찾는 기준은 하나가 아닙니다

관심 있는 label에서 최신 Issue를 고르는 것도 한 방법이지만, 실제 기여거리는 사용자가 하려는 일과 이미 지원되는 기능의 동작, 현재 구현이 가진 전제에서도 발견할 수 있습니다.

사용자가 하려는 일에서 빠진 기능을 찾습니다

Browser의 persistent storage · gluesql-js Issue #10 · @panarch / PR #13, PR #15, PR #16 · @juhee200

코드 안의 TODO보다 사용자가 GlueSQL로 무엇을 하려는지부터 볼 수도 있습니다. @juhee200이 앞서 작업한 PR #1948의 ToGlueRow와 values_from은 Rust struct를 INSERT할 때 직접 맞추던 column과 value를 줄였습니다. gluesql-js의 OPFS 작업은 브라우저에서 데이터를 계속 보관하려는 흐름에서 시작했습니다.

OPFS의 synchronous access handle은 Dedicated Worker 안에서만 사용할 수 있습니다. PR #13은 기존 browser entry point를 그대로 두고 Promise 기반 query()를 제공하는 worker entry point를 먼저 만들었습니다. 실제 storage 대신 MemoryStorage를 넣어 worker와 browser 사이의 호출 경계를 먼저 확인했습니다.

실제 Chrome review에서는 worker 종료 뒤 일부 Promise가 끝나지 않는 문제가 발견되었습니다. PR #15는 이 browser 경계를 Playwright test로 고정했고, PR #16은 임시 MemoryStorage를 redb 기반 OPFS storage로 교체했습니다. 이 과정에서 직접 pager와 recovery format을 유지하는 방식도 기존 redb engine을 재사용하는 구조로 바뀌었습니다.

세 PR은 진입점, browser test, persistent storage를 나누어 진행했습니다.

사용자 입장에서 직접 실행해 봅니다

CREATE INDEX와 composite foreign key · PR #1998, Issue #2002 · @jun02160

기능이 코드에 존재하는 것과 기대한 의미대로 동작하는 것은 다릅니다. PR #1998에서는 CREATE UNIQUE INDEX가 오류 없이 일반 index로 생성됐고, Issue #2002에서는 composite foreign key를 선언해도 첫 column만 검사했습니다. 둘 다 성공한 것처럼 보이면서 일부 의미가 사라졌습니다.

같은 관점은 정상적인 query 결과뿐 아니라 storage가 실패한 뒤의 상태에도 적용할 수 있습니다.

실패 전후의 상태와 복구 경계를 나눕니다

FileStorage migration 중단 · Issue #2004 · @jun02160

FileStorage migration은 row file을 하나씩 새 형식으로 바꾸고 마지막에 schema version을 갱신합니다. 중간에 멈추면 새 형식과 이전 형식이 섞이지만, migration이 시작됐다는 표식이 없어 다음 실행이 복구 경로를 안내하기 어렵습니다.

Issue #2004는 이를 막연한 데이터 손실 가능성으로 표현하지 않았습니다. 다시 migration을 실행하면 수렴할 수 있는 경우도 있음을 구분하고, 실패 시점을 다음 두 구간으로 나눴습니다.

계획 단계: 모든 row를 읽고 새 bytes를 준비하지만 아직 쓰지 않음
적용 단계: migration 진행 상태를 남기고 row와 schema version을 갱신함

계획 단계의 오류는 파일을 건드리기 전에 반환하고, 적용 단계의 중단은 진행 표식으로 감지해 복구하거나 다시 진행하자는 구분입니다. transaction 안에서 migration하는 Redb와 file을 하나씩 바꾸는 FileStorage의 차이도 함께 정리했습니다.

사용자의 입장에서 확인한다는 것은 성공한 결과만 실행하는 일이 아닙니다. option이 붙은 입력, 여러 column, 중간 실패 뒤 다시 여는 흐름까지 보면 코드 안에서는 드러나지 않던 차이를 발견할 수 있습니다.

아직 없던 방법을 제안해 봅니다

Tracing 기반 query observability · Issue #1958, PR #1974 · @dodok8

Application에서는 query 전체 시간을 측정할 수 있지만, 지연이 parse, plan, execute, storage 중 어디에서 발생했는지 구분하기 어려웠습니다. Issue #1958은 각 단계를 optional tracing span으로 표현하는 방법을 제안했습니다.

tracing은 기본 기능이 아니며, GlueSQL core는 span만 만들고 수집과 전송 방법은 application이 선택합니다. raw SQL이나 row처럼 민감한 값도 기본으로 기록하지 않는다는 경계를 함께 정했습니다.

PR #1974는 이 제안을 실제 span과 출력으로 보여줬습니다. Redb 내부 관찰, CLI exporter, resource benchmark까지 범위가 넓어졌기 때문에 무엇을 먼저 도입하고 무엇을 후속 작업으로 나눌지는 더 검토할 지점으로 남아 있습니다.

8월 24일 현재 PR #1974는 열려 있어 도입된 기능으로 볼 수는 없습니다. 그래도 제안과 실제 출력이 함께 있으면 maintainer는 필요성과 프로젝트가 맡을 범위를 구체적으로 비교할 수 있습니다.

설정이 적용되는 시점을 비교합니다

Coverage workflow의 event별 설정 · Issue #1949 · @panarch / PR #1954 · @aswitocom

Coverage workflow는 push와 pull_request event 모두에서 docs/** 변경을 제외하고 있었습니다. 문서만 고친 Pull Request에서 coverage를 생략하는 것은 합리적이지만, 그 PR이 병합된 뒤 main에 발생하는 push까지 생략하면 최신 HEAD의 coverage report가 만들어지지 않습니다.

PR #1954는 같은 docs/** 규칙이 어느 event에 적용되는지 비교했습니다. pull_request에는 기존 filter를 그대로 두고 push에서만 두 줄을 제거해, review 단계에서는 불필요한 작업을 줄이면서 main의 report는 실제 HEAD와 맞도록 했습니다.

코드의 이름과 실제 책임을 비교합니다

Hash join planner 이름 정리 · Issue #1966 · @panarch / PR #1988 · @MinhyukWoo

JoinPlanner라는 이름은 모든 join 실행 방식을 결정하는 것처럼 보였지만, 실제 책임은 hash join 후보를 찾는 일이었습니다. 후보가 없으면 기존 nested-loop plan을 그대로 유지했습니다.

PR #1988은 이름을 HashJoinPlanner와 plan_hash_join으로 좁혔습니다. 동작은 바꾸지 않았지만 call site만 읽어도 이 단계가 선택적인 최적화라는 사실이 드러납니다.

오래된 Issue를 현재 코드에서 다시 확인합니다

Table factor evaluability · Issue #1407 · @ding-young / PR #1961 · @red-sprout

Issue #1407은 2023년 9월에 등록되고 2026년 7월에 PR #1961로 닫혔습니다. table factor를 확인할 때 derived subquery와 SERIES의 size expression을 보지 않는 문제였습니다.

PR은 현재 main에서도 빠진 순회가 남아 있는지 먼저 확인한 뒤, 이미 있던 query와 expression 검사를 재사용해 한 파일에서 수정했습니다. 오래 열려 있었다는 사실보다 현재 코드에서 같은 재현과 type이 남아 있는지가 더 중요합니다.

한 문제를 따라가며 선행 과제를 찾습니다

Table factor에서 schemaful identifier binding까지 · @red-sprout

PR #1961을 준비하면서는 inner query의 alias가 outer query로 잘못 넘어가고, 중복 relation alias가 한쪽으로 조용히 해석되는 더 넓은 문제가 보였습니다. 원래 작업보다 범위가 커 Issue #1965로 분리했습니다.

이후의 흐름은 하나의 Issue를 고른 뒤에도 관련 작업의 순서를 다시 찾을 수 있음을 보여줍니다.

Issue #1407 → PR #1961
                    ↓ 작업 중 별도 문제 발견
              Issue #1965 → PR #1970
                                  ↓ discussion에서 선행 구조 분리
                            Issue #1976 → PR #1977
                                                ↓ review 중 최적화 문제 발견

PR #1970을 진행하면서는 planner가 알아낸 column 정보를 plan에 남기지 않아 executor가 이름을 다시 해석한다는 선행 문제가 드러났습니다. 이 책임을 먼저 정리하는 작업은 Issue #1976과 PR #1977로 분리했습니다.

PR #1977 review 중에는 positional column alias 때문에 secondary index를 찾지 못하는 Issue #1985가 나왔습니다. 결과가 틀리는 bug가 아니라 최적화 후보를 놓치는 문제로 구분하고, 임시 이름 변환 대신 #1978, #1910, #1971과의 선후 관계를 기록했습니다.

8월 24일 현재 PR #1970과 #1977, Issue #1985는 열려 있습니다. 여기서 중요한 것은 병합 결과보다 지금 해결할 문제, 먼저 필요한 구조, 이후의 최적화로 순서를 정한 과정입니다.

다른 작업을 읽다가 발견한 문제를 분리합니다

CompositeStorage::rollback() 위임 오류 · Issue #1962 · PR #1963 · @seosangwon

Issue #1962는 다른 transaction 작업인 #1959를 살펴보던 중 발견되었습니다. CompositeStorage::rollback()이 각 inner storage의 rollback()이 아니라 commit()을 호출하고 있었습니다.

실제 diff는 한 줄이었습니다.

- storage.commit()?;
+ storage.rollback()?;

한 줄이지만 transaction API의 의미를 반대로 만들던 문제였습니다. 원래 작업에 함께 넣지 않고 별도 Issue와 PR로 분리해 목적과 review 범위를 분명하게 했습니다.

테스트에서 시작하면 코드의 입구를 찾기 쉽습니다

GlueSQL의 SQL fixture는 입력과 기대 결과를 같은 파일에 기록합니다. SQL fixture를 소개한 글에서 살펴봤듯이 fixture는 regression test이면서 현재 지원 동작을 보여주는 실행 가능한 문서입니다.

문제를 재현할 수 있다면 먼저 비슷한 fixture를 찾는 것이 좋습니다.

rg -n "IN \(SELECT|SUM\(" test-suite/fixtures

검색 결과는 어느 module이 이 기능을 담당하는지보다 먼저, 프로젝트가 같은 SQL을 어떤 이름과 경계 조건으로 검증하는지 보여줍니다.

결과가 없어도 입력 구조는 남습니다

다중 column IN subquery · Issue #1880 · @panarch / PR #1936 · @ssseft

기존 IN (subquery) 평가는 subquery row에서 첫 번째 값만 꺼냈습니다. 그래서 다음 SQL은 두 column 중 id만 사용해 성공했습니다.

SELECT id
FROM T
WHERE id IN (SELECT id, name FROM T);

결과 row의 길이만 검사하면 row가 있을 때는 문제를 찾을 수 있지만, 결과가 비어 있으면 검사할 대상이 없습니다.

SELECT id
FROM T
WHERE id IN (SELECT id, name FROM T WHERE id = 0);

두 번째 query도 결과와 관계없이 두 column을 projection합니다. PR은 row가 아니라 projection 정보로 column 수를 먼저 확인하고, 결과가 있는 경우와 없는 경우를 함께 테스트했습니다. 기존 fixture가 잘못된 동작에 기대고 있던 부분과 이 상황에 맞는 전용 오류도 review에서 정리했습니다.

기존 테스트가 잘못된 동작을 기대할 수도 있습니다

Aggregate의 NULL 처리 · Issue #1897 · @devgony / PR #1912 · @kimjune01 / PR #1990 · @teddytennant

SUM, AVG, MIN, MAX 같은 aggregate는 NULL을 제외하고 계산해야 하지만, GlueSQL은 NULL을 accumulator에 넣고 있었습니다.

CREATE TABLE T (val INTEGER NULL);
INSERT INTO T VALUES (NULL), (5), (3);

SELECT SUM(val) FROM T;
-- 기대: 8
-- 당시 동작: NULL

일부 기존 fixture도 잘못된 NULL 결과를 기대하고 있었습니다. PR #1990은 기대값을 먼저 올바르게 바꿔 실패를 확인한 뒤, non-COUNT aggregate가 NULL을 건너뛰게 했습니다.

첫 시도인 PR #1912가 닫힌 뒤 async-to-sync 전환과 execution pipeline 변경으로 코드 위치가 달라졌지만, 진단과 review 내용은 PR #1990에서 현재 구조에 맞게 이어졌습니다. 닫힌 PR에서는 patch보다 재현, 필요한 invariant, review에서 정한 경계를 가져와야 합니다.

SQL이 어디에서 달라지는지 따라갑니다

SQL 하나가 실행되기까지 parser, translate, planner, executor와 storage를 거칩니다. 처음부터 모든 계층을 읽기보다 현상이 처음 달라지는 위치를 찾는 편이 효율적입니다.

관찰한 현상 먼저 살펴볼 위치
Parser는 읽지만 GlueSQL이 지원하지 않는 clause가 사라짐 translate와 TranslateError
올바른 SQL이 잘못된 relation이나 access path로 계획됨 planner와 plan unit test
계획은 맞지만 expression 결과가 잘못됨 executor/evaluate와 SQL fixture
특정 storage에서만 lifetime, lock, migration 문제가 발생함 해당 storages/* 구현과 storage test
문서의 version이나 feature가 실제 package와 다름 docs와 Cargo.toml 같은 기준 파일

translate 모듈을 소개한 글과 planner를 소개한 글은 각 계층의 역할을 더 자세히 설명합니다. 여기서는 실제 기여에서 그 경계를 어떻게 찾았는지 살펴보겠습니다.

..와 fallback branch가 버리는 정보를 찾습니다

2026년 7월과 8월에는 지원하지 않는 SQL option을 조용히 무시하지 않도록 하는 작업이 여러 statement에서 이어졌습니다.

  • CREATE TABLE option · Issue #1973 · PR #1972 · @sweetpark
  • Unsupported option의 typed enum · Issue #1975 · @panarch / PR #1980 · @sweetpark
  • Table function argument · Issue #1904 · @panarch / PR #1983 · @kwondo1017
  • Transaction clause · PR #1991 · @kwondo1017
  • CREATE INDEX option · PR #1998 · @jun02160

Parser AST는 GlueSQL이 구현한 범위보다 많은 SQL field를 가질 수 있습니다. translate 단계에서 필요한 field만 꺼내고 나머지를 ..로 버리면 코드는 간단해지지만, 사용자가 요청한 의미까지 조용히 사라질 수 있습니다.

CREATE UNIQUE INDEX가 일반 index 생성으로 바뀌고, ROLLBACK TO SAVEPOINT가 전체 ROLLBACK으로 바뀌는 것은 단순한 미지원 기능이 아닙니다. 실행이 성공했다고 보이면서 사용자가 요청한 의미와 다른 동작을 수행하기 때문입니다.

한 statement에서 이런 문제를 발견했다면 비슷한 match arm을 검색해볼 수 있습니다.

rg -n "Unsupported.*Option|Statement::Create|Statement::Rollback|\.\." core/src/translate*

검색한 모든 ..가 오류는 아닙니다. 각 field가 SQL의 의미를 바꾸는지, 구현하지 않았다면 명시적으로 거절하는지, option이 없는 기존 동작은 유지되는지를 확인해야 합니다. parser로 만들기 어려운 variant는 AST를 직접 구성해 검증할 수 있습니다.

PR #1972에서 추가한 UnsupportedCreateTableOption의 문자열 payload는 PR #1980에서 typed enum으로 바뀌었습니다. 하나의 동작 수정이 이웃 코드의 반복된 표현을 보여주고, 그 표현을 구조화하는 다음 작업으로 이어진 것입니다.

나란히 있는 두 처리 경로를 비교합니다

Schemaless CTAS rewrite · Issue #1905 · @panarch / PR #1987 · @jinwooky

Schemaless planner는 CREATE TABLE ... AS SELECT의 source query를 validate하고 있었지만, transform 단계에서는 Query, Insert, Update, Delete만 처리하고 CreateTable을 그대로 통과시켰습니다.

validate_statement:  CreateTable의 source를 확인함
transform_statement: CreateTable branch가 없음

같은 Statement를 다루는 두 함수의 branch를 나란히 놓자 빠진 경로가 드러났습니다. PR은 CreateTable에도 기존 query transform을 적용하고 unit test와 SQL fixture를 함께 추가했습니다.

Review는 정답을 검사하는 단계만이 아닙니다

Issue의 재현과 첫 구현이 타당해도 review에서 더 나은 책임 경계가 드러날 수 있습니다.

재현 하나에서 planner의 invariant까지

JOIN의 primary-key predicate · Issue #1942 · PR #1943 · @red-sprout

Issue #1942는 joined relation인 projects.id의 조건이 첫 FROM relation인 tasks의 primary-key lookup으로 잘못 적용되는 SQL을 제시했습니다. relation 순서를 바꾸면 결과도 달라졌습니다.

현재 main에서 재현한 뒤에는 primary-key 이름이 다른 경우, 첫 relation에 key가 없는 경우, unqualified identifier와 column alias까지 같은 원인의 경계로 확인했습니다.

첫 구현은 JOIN 전체의 primary-key 정보를 공통 context에 넣었습니다. 하지만 실제 lookup은 첫 physical relation에만 설치할 수 있어, context가 실행할 수 없는 상태까지 표현한다는 문제가 review에서 드러났습니다.

최종 구조는 첫 relation에 안전하게 연결할 수 있을 때만 lookup 후보를 만들고 WHERE에서 predicate를 제거합니다. 그렇지 않으면 원래 selection을 남깁니다. SQL 의미와 planner의 선택도 각각 integration test와 unit test로 나눠 확인했습니다.

Review에서 구조가 크게 바뀌었다고 첫 접근이 무의미한 것은 아닙니다. 재현과 구현이 있었기 때문에 실제로 필요한 상태를 비교할 수 있었습니다.

병합된 PR 주변에는 다음 작업이 남습니다

새로운 기능이 병합된 직후에는 아직 고려하지 못한 입력과 API 경계가 가장 잘 보입니다. 최근 PR의 diff와 review를 읽는 것은 새로운 Issue를 찾는 좋은 방법입니다.

기능, 안전성, generic 지원을 나눕니다

ToGlueRow 흐름 · Issue #1849 · @pragmaxim / PR #1948 · @juhee200 / Issue #1951 · @panarch / PR #1955 · @ShreyasUday

Issue #1849는 Rust struct를 INSERT value로 바꾸는 ToGlueRow와 Query Builder의 values_from을 제안했고, PR #1948로 구현되었습니다.

Review에서는 column 수와 value 수가 달라지거나 rename이 중복 column을 만드는 안전성 문제가 발견됐습니다. 잘못된 row를 만들 수 있는 이 두 경우는 첫 PR에서 막았습니다.

반면 generic과 lifetime 지원은 별도 Issue #1951과 PR #1955로 분리했습니다. 비슷해 보이는 FromGlueRow 변경도 review에서 제외해 ToGlueRow 범위만 남겼습니다.

현재 API가 잘못된 값을 만들 수 있는 문제는 지금 막고, 독립적인 type 지원은 후속 작업으로 남긴 흐름입니다.

첫 기능과 최적화를 분리합니다

Regex matching · Issue #1997 · PR #2001 · Issue #2005 · PR #2006 · @red-sprout

정규식은 여러 SQL interface가 있지만 Issue #1997은 첫 범위를 PostgreSQL의 ~, ~*, !~, !~* matching으로 제한하고 capture, replace, 다른 dialect syntax를 제외했습니다.

PR #2001은 하나의 expression이 지나가는 경로를 보여줍니다.

SQL parser
→ translate
→ AST와 plan expression
→ planner
→ executor evaluation
→ SQL fixture와 Query Builder test

기능은 여러 계층을 지나지만 범위는 matching 하나로 묶었습니다. 같은 pattern을 row마다 compile하는 성능 문제는 Issue #2005와 PR #2006으로 분리했습니다. 8월 24일 현재 PR #2006은 review 중이므로 여기서는 병합 결과가 아니라 후속 범위를 독립시킨 사례로 봅니다.

큰 기능은 변경 파일 수보다 하나의 값이 계층을 어떻게 지나 실제 의미를 얻는지 따라가면 읽기 쉽습니다. GlueSQL의 typed plan과 executor 관계는 실행 파이프라인을 소개한 글에서도 이어서 볼 수 있습니다.

실제로 탐색할 때 사용할 순서

지금까지의 사례를 하나의 작업 순서로 정리하면 다음과 같습니다.

1. 관심 있는 동작을 하나 고릅니다

SQL 문법, planner, storage, Rust API, test suite, 문서 중 먼저 읽고 싶은 영역을 고릅니다. “쉬운 Issue”라는 label보다 이미 알고 있거나 더 알고 싶은 영역이 있는 편이 검색 결과를 판단하기 쉽습니다.

관심 영역을 골랐다면 다음 질문에서 시작할 수 있습니다.

  • 사용자가 한 가지 작업을 끝내기 위해 직접 해야 하는 변환이나 설정은 무엇인가?
  • 지원된다고 보이는 기능을 실제로 실행하면 기대한 의미로 동작하는가?
  • 프로젝트에 아직 없지만 문제를 이해하거나 사용하는 데 도움이 될 방법은 무엇인가?

2. 현재 main에서 가장 짧은 입력으로 확인합니다

Issue의 예제를 그대로 실행한 뒤 불필요한 table과 column, row를 줄입니다. 특정 storage에서만 발생하는지 MemoryStorage에서도 같은지 구분합니다. 오래된 Issue라면 type과 file 경로가 바뀌었는지도 확인합니다.

3. 비슷한 테스트를 먼저 찾습니다

SQL 문제라면 test-suite/fixtures, planner의 선택이라면 planner unit test, storage lifecycle이라면 해당 storage test를 먼저 봅니다. 새 테스트가 어느 위치에 있어야 하는지도 구현 범위의 일부입니다.

4. 나란히 있는 처리 경로를 비교합니다

  • 이미 지원되는 sibling expression이나 statement
  • validate와 transform처럼 같은 type을 다루는 두 단계
  • plain 입력과 option이 추가된 입력
  • schemaful과 schemaless 경로
  • eager한 구현과 interface가 기대하는 lazy 동작

비교 대상이 있으면 전체 구조를 처음부터 설계하지 않고 프로젝트가 이미 사용하는 패턴을 따라갈 수 있습니다.

5. 관련 Issue와 review discussion을 연결합니다

현상에 사용한 SQL 문구만 검색하지 말고, 원인을 좁히며 찾은 type과 함수 이름으로 열린 Issue와 닫힌 Issue를 함께 찾아봅니다. PR review에서 같은 책임 경계를 다룬 discussion이 있었는지도 확인합니다.

찾은 내용은 다음처럼 구분할 수 있습니다.

  • 지금 보고 있는 현상을 이미 다루는 작업
  • 현재 수정에 앞서 필요한 자료 구조나 책임 경계
  • correctness를 고친 뒤 별도로 다룰 최적화
  • 원래 작업과 독립적으로 재현하고 review할 문제

관련 Issue가 많다는 이유로 모두 먼저 해결해야 하는 것은 아닙니다. 현재 작업이 무엇에 의존하고 무엇을 의도적으로 미루는지 알 수 있으면 첫 범위를 정하기 쉬워집니다.

6. 첫 PR의 경계를 한 문장으로 적습니다

예를 들면 다음과 같습니다.

ORDER BY expression도 기존 expression scanner로 순회하고, scalar subquery schema dependency를 regression test로 남긴다.

이 문장에 들어가지 않는 cache, refactor, 다른 statement, 새로운 public API는 후속 작업인지 판단합니다.

7. 막힌 지점을 해결책 대신 상태로 공유합니다

완성된 설계를 준비할 필요는 없습니다. 다음 정도를 남기면 현재 위치에서 함께 판단할 수 있습니다.

관심 있는 작업:
재현한 입력과 현재 결과:
찾아본 Issue와 Pull Request:
읽어본 테스트와 코드:
판단이 필요하거나 막힌 부분:

“어디부터 봐야 할지 모르겠다”보다 ORDER BY fixture는 찾았지만 schema를 모으는 위치를 모르겠다거나, translate에서 field가 사라지는 것은 찾았지만 허용해야 하는 값인지 판단이 필요하다고 적으면 다음 탐색이 구체적이 됩니다.

기여는 하나의 PR보다 긴 흐름으로 이어집니다

이번에 살펴본 사례에서는 한 사람이 Issue를 등록하고 다른 사람이 구현하기도 했습니다. contributor가 직접 재현과 Issue, PR을 모두 이어간 경우도 있고, review에서 발견한 범위를 다음 사람이 별도 PR로 완성한 경우도 있습니다. 먼저 시도한 PR이 코드 구조 변경으로 닫힌 뒤 그 진단을 현재 코드에 맞춰 이어간 사례도 있었습니다.

따라서 기여의 시작을 “내가 해결할 수 있는 Issue를 고르는 일”로만 볼 필요는 없습니다.

  • 사용자가 한 가지 작업을 끝내는 데 반복하는 변환과 설정을 찾는 일
  • 예상과 다른 동작을 짧은 SQL로 줄이는 일
  • 오래된 Issue가 현재도 유효한지 확인하는 일
  • 관련 fixture와 code path를 연결하는 일
  • 프로젝트에 아직 없던 방법을 코드와 사용 예시로 제안하는 일
  • 작업 중 발견한 문제와 기존 Issue의 선후 관계를 정리하는 일
  • 첫 PR에서 다룰 범위와 제외할 범위를 정하는 일
  • review에서 나온 후속 작업을 독립적인 Issue로 남기는 일

처음부터 설명과 구현이 완벽할 필요는 없습니다. Issue에는 재현한 내용과 궁금한 점을, PR에는 이번에 고치려는 범위와 확인이 필요한 부분을 적어 두면 됩니다. 확신이 들 때까지 혼자 오래 붙잡고 있기보다, 현재까지 확인한 내용을 공유하면 review에서 함께 정리할 수 있습니다.

이 과정이 연결되면 아직 전체 구현을 맡지 않더라도 다음 사람이 시작할 수 있는 위치가 분명해집니다.

GlueSQL 전체를 이해한 뒤 기여하는 것이 아니라, 하나의 현상을 재현하고 테스트와 코드를 따라가며 이해할 범위를 넓혀 갑니다.
