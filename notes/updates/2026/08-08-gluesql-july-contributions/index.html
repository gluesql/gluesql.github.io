GlueSQL 월간 기여 기록: 2026년 7월

프로젝트의 한 달을 돌아보면 새로운 기능이나 가장 큰 변경부터 떠올리기 쉽습니다. 하지만 실제 변화는 서로 다른 크기의 Pull Request가 이어지며 만들어집니다. 눈에 보이는 기능을 추가하는 작업도 있고, 잘못된 결과를 막거나 테스트와 문서를 다음 사람이 읽기 좋게 만드는 작업도 있습니다.

2026년 7월에는 GlueSQL 저장소에 16개의 Pull Request가 병합되었습니다. 작성자는 모두 11명입니다. 하나의 거대한 기능이 7월을 대표했다기보다, 쿼리의 정확성과 오류 처리, 스토리지의 안정성과 성능, Rust API와 기여 환경이 여러 방향에서 함께 다듬어진 달이었습니다.

집계 항목 2026년 7월
병합된 Pull Request 16개
Pull Request 작성자 11명
집계 기준 GitHub의 병합 시각

이 글은 2026년 7월 1일부터 31일까지 병합된 Pull Request를 기준으로 합니다. 7월보다 먼저 시작했더라도 7월에 병합된 작업은 포함하고, 아직 열려 있거나 병합되지 않고 닫힌 작업은 포함하지 않았습니다. Issue와 Discussion, 병합되지 않은 제안까지 다루는 프로젝트 전체 활동 기록이라기보다, 실제 코드베이스에 들어온 변화를 PR을 통해 돌아보는 월간 기록입니다.

SQL이 조용히 잘못 동작하지 않도록

데이터베이스에서 지원하지 않는 입력을 오류로 돌려주는 일은 새로운 SQL을 실행하는 것만큼 중요합니다. 실행할 수 없는 구문을 받아들인 뒤 일부만 사용하거나, 잘못된 계획으로 다른 결과를 돌려주면 사용자는 성공한 쿼리를 더 의심하기 어렵기 때문입니다.

다중 column IN subquery 오류 처리 · #1936 · @ssseft

IN (subquery)에 column이 여러 개인 subquery가 들어오면 기존에는 첫 column만 사용했습니다. 이제는 이 입력을 거절하고, 결과 row가 없는 경우에도 projection 자체가 두 column이라면 같은 오류를 반환합니다. 실제 데이터가 우연히 비어 있는지와 관계없이, IN이 요구하는 입력 구조를 먼저 확인하게 되었습니다.

JOIN과 table factor 계획 보완 · #1943, #1961 · @red-sprout

JOIN query에서는 primary key 조건을 잘못된 relation의 접근 경로로 사용하는 문제를 수정했습니다. Planner가 안전하게 연결할 수 없는 조건은 WHERE에 그대로 남기고, 첫 번째 FROM relation에 속한 조건만 primary key 조회에 사용합니다. Derived table의 subquery와 SERIES 크기 표현식도 안쪽까지 살펴보고 실행 전에 평가할 수 있는지를 확인하도록 보완했습니다.

두 작업은 모두 SQL의 겉모양만 확인하지 않고, column과 relation이 실제로 어느 범위에 속하는지 계획 단계에서 확인하는 변화입니다. GlueSQL planner가 query를 실행 가능한 결정으로 바꾸는 과정은 planner를 살펴본 글에서 더 자세히 볼 수 있습니다.

지원하지 않는 SQL option의 오류 구조화 · #1972, #1980 · @sweetpark

GlueSQL이 지원하지 않는 CREATE TEMPORARY TABLE, CREATE TABLE ... LIKE, CREATE TABLE ... CLONE option을 조용히 무시하지 않고 translate error로 돌려주도록 했습니다. 이어서 여러 unsupported option 오류가 문자열 대신 전용 enum을 사용하게 바뀌었습니다. 사용자에게 보이는 메시지는 유지하면서, 코드 안에서 가능한 오류 이유를 compiler가 확인할 수 있는 닫힌 목록으로 만들었습니다.

Parser가 읽을 수 있는 문법과 GlueSQL이 지원하는 SQL은 같지 않습니다. translate 모듈을 살펴본 글에서 설명한 이 경계가 7월에는 구체적인 오류와 type으로 더 분명해졌습니다.

스토리지는 서로 다른 방식으로 단단해졌습니다

GlueSQL은 공통 Store traits 위에서 여러 스토리지를 연결하지만, 파일 형식과 잠금, transaction과 scan 성능은 각 구현이 별도로 다뤄야 합니다. 7월의 storage 관련 PR 네 개도 서로 다른 종류의 문제를 해결했습니다.

Redb v3 storage format과 migration · #1901 · @edomaur

새로운 Redb v3 storage format을 도입하고 기존 Redb 파일을 옮길 migration 경로를 마련했습니다. 새 형식을 사용하는 것만으로 끝내지 않고, 이전 형식의 데이터를 보존하며 이동하는 과정과 migration이 필요한 경우의 오류를 함께 다뤘습니다. 이 PR은 5월에 시작되었지만 실제 코드베이스에는 7월에 들어왔습니다.

Sled lock 해제 대기 · #1944 · @panarch

Sled가 flush 뒤 잠시 database file lock을 유지할 때, storage를 즉시 다시 여는 작업이 실패하지 않도록 lock 해제를 기다렸다가 재시도하게 했습니다. 일반적인 open과 migration 경로가 같은 동작을 사용하고, lock 해제와 timeout, 다른 종류의 오류를 각각 검증합니다.

CompositeStorage rollback 수정 · #1963 · @seosangwon

CompositeStorage::rollback()이 내부 storage의 commit()을 호출하던 코드를 rollback() 호출로 바로잡았습니다. 변경된 코드는 한 줄이지만, transaction을 되돌린다는 API의 의미를 지키는 데 필요한 수정입니다. 변경한 줄의 수만으로 기여의 중요도를 판단하기 어려운 사례이기도 합니다.

Parquet row streaming · #1968 · @dgg1dbg

Parquet scan을 시작할 때 모든 row를 Vec으로 읽지 않고, 필요한 row를 iterator에서 순서대로 가져오도록 바꿨습니다. 전체 결과를 미리 materialize하지 않으므로 LIMIT처럼 앞부분만 필요한 query는 나머지 row를 읽기 전에 멈출 수 있습니다.

PR에 기록된 250,000 row, 5.8 MiB 파일의 warm-cache benchmark에서는 다음과 같은 차이가 측정되었습니다. 이 수치는 모든 Parquet workload의 일반적인 성능을 뜻하기보다, 전체 row를 먼저 읽던 비용이 query 종류에 따라 어떻게 달라졌는지를 보여줍니다.

Query 변경 전 변경 후
SELECT * FROM Foo LIMIT 10 71.0 ms 1.11 ms
SELECT COUNT(*) FROM Foo 83.9 ms 74.9 ms

공통 SQL test suite만으로 storage 고유의 파일 처리와 동시성, 성능까지 모두 보장할 수는 없습니다. 7월의 변화는 Store traits 글에서 구분했던 공통 동작 계약과 storage별 책임이 실제 기여에서 어떻게 함께 다뤄지는지 보여줍니다.

Rust struct와 GlueSQL row 사이의 거리를 줄였습니다

SQL을 실행하는 기능뿐 아니라 Rust application에서 row를 넣고 꺼내는 방법도 이어서 개선되었습니다.

ToGlueRow와 values_from · #1948 · @juhee200

Rust struct에서 column metadata와 row value를 만드는 ToGlueRow derive macro를 추가했습니다. Query Builder의 values_from을 사용하면 struct 목록을 insert할 column과 value로 변환할 수 있고, field 이름과 column 이름이 다를 때 rename도 지정할 수 있습니다. 비어 있는 입력과 field 수가 맞지 않는 경우의 오류, compile-fail과 runtime 동작도 함께 검증했습니다.

Derive의 generic 지원 · #1955 · @ShreyasUday

ToGlueRow derive가 lifetime과 type, const generic, where clause를 보존하도록 확장했습니다. 단순한 struct 예제에서 동작하는 macro를 실제 Rust type 정의에도 적용할 수 있도록 경계를 넓힌 작업입니다.

FromGlueRow module 분리 · #1956 · @juhee200

반대 방향의 변환을 담당하는 FromGlueRow derive 구현을 별도 module로 분리했습니다. 새로운 API를 추가한 PR과 generic 지원, 내부 module 정리가 며칠 사이에 이어지며 row 변환 기능의 사용성과 유지보수 구조를 함께 다듬었습니다.

GlueSQL의 Query Builder가 실행 계획을 Rust API로 구성하는 입구라면, ToGlueRow와 FromGlueRow는 application의 Rust data와 GlueSQL row를 연결하는 입구입니다. 서로 다른 계층의 API지만, SQL 문자열만이 아닌 Rust type을 통해 GlueSQL을 사용하는 범위를 넓힌다는 점에서 연결됩니다.

다음 기여를 위한 기반도 바뀌었습니다

사용자가 바로 접하는 기능이 아니더라도, 테스트와 coverage, 문서가 바뀌면 이후 기여를 시작하고 검토하는 방법이 달라집니다.

SQL fixture 전환 · #1941 · @panarch

SQL 기반 integration test 184개를 Rust test body에서 .sql fixture로 옮겼습니다. 372개 파일이 바뀐 7월의 가장 큰 PR이지만, 목적은 변경량 자체가 아니라 실행할 SQL과 기대 결과를 같은 자리에서 읽을 수 있게 만드는 것이었습니다. 이 작업의 구조와 기준은 SQL fixture 글에 별도로 정리했습니다.

Coverage 도구 전환 · #1938 · @panarch

Coverage 수집 도구를 grcov에서 Cargo 명령과 가까운 cargo-llvm-cov로 바꿨습니다. CI와 비슷한 측정을 contributor가 로컬에서도 재현하기 쉬운 형태로 정리한 변화입니다.

main coverage report 갱신 · #1954 · @aswitocom

문서만 바뀐 commit이 main에 들어와도 coverage workflow가 실행되게 했습니다. Pull Request 단계에서 불필요한 coverage 실행은 피하면서, 병합된 main의 coverage report는 실제 HEAD와 맞도록 조정했습니다.

Rust getting started 문서 갱신 · #1940 · @Bortlesboat

Rust getting started 문서의 GlueSQL version을 당시 현재 release인 0.19.0으로 갱신하고, 기본으로 제공되는 storage feature 목록을 crate manifest와 맞췄습니다. 문서의 설치 예제가 현재 package와 어긋나지 않도록 유지하는 것도 사용자가 프로젝트를 처음 실행하게 만드는 기여입니다.

11명이 만든 16개의 변화

7월에 병합된 Pull Request를 작성한 사람은 @aswitocom, @Bortlesboat, @dgg1dbg, @edomaur, @juhee200, @panarch, @red-sprout, @seosangwon, @ShreyasUday, @ssseft, @sweetpark입니다.

어떤 PR은 새로운 API를 추가했고, 어떤 PR은 잘못된 query 결과나 transaction 동작을 바로잡았습니다. 수백 개의 파일을 옮긴 작업과 한 줄을 수정한 작업, 오래 진행한 storage migration과 며칠 사이 이어진 derive macro 개선이 모두 같은 달의 코드베이스를 만들었습니다.

앞으로도 월간 기여 기록에서는 가장 큰 PR을 순서대로 나열하기보다, 병합된 변화가 한 달 동안 GlueSQL을 어느 방향으로 움직였는지 살펴보려고 합니다. 7월에는 SQL을 더 엄격하게 해석하고, storage의 경계 조건을 보완하고, Rust API와 다음 기여의 기반을 함께 다듬었습니다.

월간 기여 기록은 가장 큰 변경을 뽑는 글이 아니라, 서로 다른 크기의 기여가 한 달 동안 프로젝트를 어떻게 움직였는지 남기는 기록입니다.
