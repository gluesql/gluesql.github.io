GlueSQL은 Store traits로 스토리지와 SQL 엔진을 연결합니다

GlueSQL is quite sticky. It sticks to anything.

이 문장은 GlueSQL GitHub 저장소에 적힌 프로젝트의 슬로건입니다. GlueSQL이라는 이름을 이용한 표현이지만, 동시에 프로젝트가 지향하는 구조를 설명합니다.

일반적인 데이터베이스에서 스토리지 엔진은 내부에 포함된 구현입니다. 사용자는 데이터베이스 클라이언트나 연결을 통해 완성된 데이터베이스에 접근하고, 데이터가 저장되는 방식을 직접 연결하지는 않습니다.

GlueSQL은 데이터를 하나의 정해진 스토리지로 가져오게 하는 대신, SQL 실행 계층이 여러 데이터 환경에 연결될 수 있는 구조를 만들고 있습니다. 메모리, CSV와 JSON 같은 파일, key-value 데이터베이스와 NoSQL 데이터베이스, 파일 시스템과 remote API까지 데이터를 읽고 쓰는 방법은 서로 다릅니다. 정형 데이터와 schemaless data처럼 데이터의 형태도 다르고, 읽기 전용부터 index와 transaction까지 제공할 수 있는 기능의 범위도 다릅니다.

슬로건의 anything은 이 모든 환경을 이미 완전하게 지원한다는 선언이 아닙니다. 데이터를 GlueSQL의 Schema, Key, Value로 읽고 쓰는 방법을 연결할 수 있다면, 공통으로 구현된 SQL 동작을 그 위에서도 사용할 수 있도록 연결 가능한 범위를 계속 넓혀가겠다는 방향에 가깝습니다.

이 방향을 실제 구현으로 옮기는 가장 기본적인 접점이 Store traits입니다. GlueSQL은 스토리지 인터페이스만 공개하는 데서 그치지 않습니다.

  • planner와 executor가 SQL의 의미를 공통으로 처리합니다.
  • 기능을 여러 trait으로 나누고 기본 구현을 제공해 스토리지가 필요한 범위부터 구현할 수 있게 합니다.
  • 같은 SQL 동작을 만족하는지 확인할 수 있는 test suite를 함께 제공합니다.

즉 Store traits는 GlueSQL이 다양한 환경에 붙을 수 있게 하는 접점이고, 공통 실행 계층과 test suite는 실제로 붙이는 과정의 구현 부담을 줄이는 기반입니다.

이전 글에서는 외부 SQL parser가 만든 AST를 GlueSQL의 내부 표현으로 옮기는 translate 모듈을 살펴봤습니다. translate가 SQL 문법과 GlueSQL 내부의 경계라면, Store traits는 planner와 executor를 실제 데이터에 연결하는 경계입니다.

SQL
→ parse
→ translate
→ planner
→ executor
→ Store traits
→ 스토리지

이제 이 접점이 코드에서 어떻게 나뉘어 있고, executor와 planner가 어떤 역할을 가져가는지, 새로운 스토리지가 공통 test suite를 어떻게 재사용하는지 살펴보겠습니다.

제공되는 스토리지를 쓰거나 직접 연결할 수 있습니다

GlueSQL은 Memory, CSV, JSON, Sled 같은 기본 스토리지 구현을 제공하며, 필요에 맞는 구현을 골라 바로 사용할 수 있습니다. 하지만 GlueSQL이 붙을 수 있는 대상이 이 목록으로 정해지는 것은 아닙니다.

자신이 관리하는 스토리지나 서비스의 데이터 접근 방식을 Store traits로 연결하면, 그 환경에서도 GlueSQL의 SQL과 Query Builder를 사용할 수 있습니다. 새로운 환경에 SQL을 제공하기 위해 parser와 planner, expression evaluator와 executor를 다시 만들 필요 없이, 스토리지가 schema와 row를 읽고 쓰는 데 필요한 부분부터 구현하면 됩니다.

기본적인 읽기와 쓰기는 Store와 StoreMut에서 시작하고, index나 transaction 같은 기능은 필요에 따라 추가할 수 있습니다. 구현한 스토리지에는 GlueSQL의 공통 test suite를 실행해 같은 SQL이 기대한 결과를 만드는지도 확인할 수 있습니다. 기본 제공 스토리지는 바로 사용할 수 있는 구현인 동시에, 누구나 자신의 환경에 SQL을 연결할 때 참고할 수 있는 예시입니다.

읽기 동작은 작은 Store trait에서 시작합니다

Store는 읽기 동작을 위한 네 가지 메서드를 요구합니다.

기능은 크게 세 가지 역할로 정리할 수 있습니다.

  • table의 schema를 가져옵니다.
  • Key를 이용해 하나의 row를 가져옵니다.
  • table에 저장된 row를 순서대로 scan합니다.

이 메서드들은 WHERE clause를 해석하거나 JOIN과 aggregate를 실행하는 API가 아닙니다. 스토리지는 GlueSQL의 Key와 Value 형태로 데이터를 읽을 방법만 제공합니다.

예를 들어 MemoryStorage와 CsvStorage가 데이터를 보관하고 읽는 방식은 서로 다릅니다. 하지만 Store trait을 통과한 뒤 executor가 받는 schema와 row의 형태는 같습니다.

이 작은 공통 형식이 있으면 GlueSQL은 스토리지가 메모리인지 파일인지 알지 못해도 그 위에서 row를 읽고 SQL expression을 평가할 수 있습니다.

SQL의 의미는 executor가 공통으로 처리합니다

다음 SQL을 실행한다고 생각해보겠습니다.

UPDATE Users
SET active = TRUE
WHERE last_login < '2026-01-01';

스토리지가 이 SQL을 직접 해석해 자체 쿼리로 바꾸는 것은 아닙니다. GlueSQL의 executor가 schema를 확인하고, WHERE expression을 만족하는 row를 찾고, column type과 constraint를 검증한 뒤 변경할 row를 구성합니다. 스토리지에는 마지막으로 계산된 key와 row를 저장하는 작업이 전달됩니다.

같은 방식으로 GlueSQL core는 다음 동작을 여러 스토리지에서 공통으로 처리합니다.

  • projection, filter, JOIN과 aggregate
  • data type, nullability와 constraint 검증
  • schemaless data와 SQL expression 평가

StoreMut은 executor가 계산한 결과를 스토리지에 반영할 수 있도록 schema와 row를 추가하고 변경하거나 삭제하는 메서드를 제공합니다.

새로운 스토리지를 구현할 때 UPDATE, DELETE, foreign key 검증을 각각 처음부터 다시 구현할 필요는 없습니다. 기본적인 읽기와 쓰기를 GlueSQL의 데이터 모델에 연결하면, SQL의 동작은 core의 같은 코드 경로를 이용합니다.

planner도 스토리지와 함께 동작합니다

Store traits가 executor의 마지막 단계에서만 사용되는 것은 아닙니다. 기본 Planner는 스토리지에서 schema를 가져와 table과 column을 검증하고, 쿼리를 실행할 구조를 준비합니다.

스토리지가 index 같은 별도 최적화를 제공한다면 planner도 확장할 수 있습니다. 공통 planning 과정은 재사용하면서 스토리지가 가진 조회 방법을 실행 계획에 반영하는 구조입니다.

따라서 Store traits는 스토리지에서 값을 읽고 쓰는 API이면서, planner가 스토리지의 schema와 기능을 실행 계획에 반영하는 연결점이기도 합니다.

기능을 여러 trait으로 나누었습니다

Store 하나에 모든 스토리지 기능을 넣으면 간단한 스토리지도 transaction과 index를 모두 구현해야 합니다. GlueSQL은 기능별로 trait을 나누어 필요한 범위를 구분합니다.

Trait 담당하는 기능
Store, StoreMut schema와 row 읽기, 쓰기
AlterTable table과 column 변경
Index, IndexMut index 조회, 생성과 삭제
Transaction begin, commit과 rollback
Planner 스토리지 기능을 반영한 planning
그 외 선택적인 trait metadata와 custom function 등

모든 스토리지가 모든 기능을 실제로 제공해야 하는 것은 아닙니다. 지원하지 않는 기능은 not supported로 구분하고, 필요한 기능부터 선택해 연결할 수 있습니다.

반대로 여러 기능에는 Store와 StoreMut을 이용한 기본 구현이 제공됩니다. 공통 동작으로 시작하고, 스토리지가 더 적합한 방법을 가지고 있다면 별도 구현으로 바꿀 수 있습니다.

같은 SQL을 여러 스토리지에서 검증합니다

Trait 정의만으로는 새로운 스토리지가 GlueSQL에서 올바르게 동작하는지 알기 어렵습니다. 메서드 signature가 맞아 컴파일된다는 사실은 INSERT 뒤의 SELECT, primary key 충돌, nullable column이나 aggregate가 기대한 결과를 만드는지 보장하지 않습니다.

GlueSQL은 사용자 정의 스토리지에서도 재사용할 수 있는 gluesql-test-suite를 별도 crate로 제공합니다.

스토리지 구현자는 Tester에 테스트용 스토리지를 만드는 방법을 연결한 뒤 공통 테스트 세트를 등록할 수 있습니다.

generate_store_tests!(test, MyStorageTester);

이 테스트 세트에는 SQL fixture와 Query Builder를 이용한 공통 동작이 함께 등록되어 있습니다.

7월 20일에 SQL fixture로 재구성한 test suite가 여기서 스토리지 동작 계약의 실제 예시가 됩니다.

CREATE TABLE Test (
    id INTEGER,
    name TEXT
)
-- @expect: ok

INSERT INTO Test VALUES (1, 'Hello')
-- @expect: ok

SELECT * FROM Test
-- @expect:
-- | id: I64 | name: Str |
-- | ------- | --------- |
-- | 1       | "Hello"   |

같은 fixture는 서로 다른 기본 스토리지에서 반복해서 실행됩니다. 스토리지를 준비하는 방법은 달라도 검증하는 SQL과 기대 결과는 공유합니다.

Test suite는 기능 사이의 조합도 확인합니다. 예를 들어 transaction 안에서 row와 index가 함께 변경되었다가 rollback되면 둘 다 이전 상태로 돌아가야 합니다. 개별 기능뿐 아니라 함께 사용할 때의 일관성까지 검증함으로써 Store traits를 메서드 목록이 아닌 동작의 계약으로 만듭니다.

공통 동작 계약이 모든 차이를 없애지는 않습니다

Store traits를 구현하고 test suite를 통과해도 모든 스토리지가 같은 성능과 운영 특성을 갖는 것은 아닙니다.

GlueSQL의 공통 실행 계층은 여러 스토리지에서 같은 SQL 동작을 제공하기 위해 table scan이나 row 단위 처리를 사용할 수 있습니다. CSV의 UPDATE처럼 파일 전체를 다시 써야 하는 스토리지도 있고, remote API에서는 여러 번의 row 조회가 큰 비용이 될 수도 있습니다. 반면 key-value 데이터베이스는 key lookup과 index를 이용해 일부 쿼리를 더 효율적으로 실행할 수 있습니다.

이러한 차이를 모두 스토리지 구현에 맡기고 끝내는 것은 아닙니다. 더 다양한 데이터 모델과 워크로드를 제대로 지원하려면 GlueSQL의 planner와 실행 계층도 스토리지의 특성을 표현하고 활용할 수 있도록 계속 발전해야 합니다.

예를 들어 ParquetStorage를 연결하면 Parquet 파일에 SQL을 사용할 수 있지만, 그것만으로 OLAP 워크로드에 적합한 실행 방식까지 갖추는 것은 아닙니다. 분석에 필요한 데이터 타입과 연산을 넓히고, 필요한 column만 읽거나 조건을 스토리지에 전달하는 planning과 execution을 지원해야 Parquet 같은 columnar 스토리지의 장점을 더 잘 활용할 수 있습니다.

이 과정에서 특정 스토리지에만 필요한 최적화와 여러 스토리지가 함께 사용할 수 있는 기능을 구분해 공통 계층과 확장 지점을 계속 조정하게 됩니다. GlueSQL이 하나의 데이터 모델에만 집중하지 않고 여러 모델과 스토리지를 같은 인터페이스로 지원하려는 만큼, planner와 실행 계층에서 풀어야 할 일도 계속 생깁니다.

Test suite가 확인하는 범위도 구분해야 합니다.

  • 공통 SQL 입력이 같은 결과와 오류를 만드는지 검증합니다.
  • Store traits의 메서드가 planner와 executor에서 함께 동작하는지 검증합니다.
  • 스토리지 고유의 성능, 데이터 내구성, 동시성과 장애 복구까지 보장하지는 않습니다.

공통 test suite를 통과한 뒤에도 스토리지의 직렬화와 파일 처리, transaction isolation처럼 구현에만 존재하는 동작은 별도 테스트가 필요합니다.

GlueSQL은 스토리지 차이를 숨겨 모두 같은 구현으로 만들기보다, 공통으로 제공할 SQL 의미와 스토리지가 책임질 부분 사이에 경계를 둡니다. 기본 구현과 test suite로 시작할 범위를 넓게 제공하고, 스토리지별 최적화와 함께 여러 환경에 공통으로 필요한 기능은 planner와 실행 계층에서 계속 보완해갑니다.

처음부터 Store가 구조의 중심에 있었습니다

Store는 여러 스토리지가 생긴 뒤 추가된 플러그인 인터페이스가 아닙니다. GlueSQL의 첫 구조부터 parser, translator, executor와 실제 데이터를 연결하는 중심에 있었습니다.

메서드와 데이터 모델은 이후 계속 바뀌었고, 읽기와 쓰기부터 transaction과 index 같은 기능이 여러 trait으로 나뉘었습니다.

하지만 SQL을 해석하고 실행하는 공통 계층과 실제 데이터를 다루는 스토리지를 trait으로 연결한다는 기본 구조는 처음부터 이어져 왔습니다.

It sticks to anything은 모든 스토리지를 이미 지원한다는 완료 선언이 아닙니다. 데이터를 읽고 쓰는 방법을 연결할 수 있다면 그 위에 SQL 실행 계층을 올릴 수 있도록, 연결 가능한 데이터 환경의 범위를 계속 넓혀가겠다는 방향입니다.

새로운 스토리지를 추가한다는 것은 SQL 엔진을 처음부터 만드는 일이 아닙니다. 스토리지의 데이터 모델을 GlueSQL의 Schema, Key, Value에 연결하고, 공통 planner와 executor를 재사용하며, test suite를 통해 이미 구현된 SQL의 의미가 그 위에서도 유지되는지 확인하는 작업입니다.

Store traits는 GlueSQL이 새로운 데이터 환경에 붙는 방법을 정의합니다. 기능별 trait과 기본 구현, 기본 제공 스토리지와 공통 test suite를 함께 발전시키는 것은 그 접점을 선언하는 데서 그치지 않고 실제로 구현하기 좋은 구조로 만들어가는 과정입니다.
