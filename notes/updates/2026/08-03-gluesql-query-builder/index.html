GlueSQL의 Query Builder는 실행 계획을 직접 만듭니다

Rust에서 Query Builder라고 하면 SQL 문자열과 파라미터를 만드는 도구를 먼저 떠올릴 수 있습니다. sqlx::QueryBuilder는 실행할 SQL을 동적으로 구성하고, SeaQuery는 같은 API로 MySQL과 PostgreSQL, SQLite에 맞는 SQL을 생성합니다.

GlueSQL의 Query Builder도 메서드 체이닝(method chaining)으로 쿼리를 작성한다는 점에서는 비슷해 보입니다. 하지만 만들려는 결과가 다릅니다.

범용 Query Builder가 외부 데이터베이스에 전달할 SQL을 만든다면, GlueSQL의 Query Builder는 GlueSQL이 실행할 StatementPlan을 직접 만듭니다. 단순히 SQL을 편하게 작성하기 위한 보조 API가 아니라, 엔진 내부의 실행 계획을 Rust API로 구성하는 또 하나의 입력 방식입니다.

이번 글에서는 GlueSQL이 기존 ORM이나 범용 Query Builder를 그대로 사용하는 대신 별도의 Query Builder를 만든 이유를 살펴봅니다. 개발자가 실행 계획을 명시할 수 있는 구조와, 쿼리 작성 과정을 상태 머신(state machine) 형태의 타입 그래프(type graph)로 표현하려는 설계가 중심에 있습니다.

SQL 문자열이 아니라 GlueSQL의 내부 표현이 필요했습니다

일반적인 Query Builder는 다음 경로를 사용합니다.

Rust API
→ SQL 문자열과 파라미터 생성
→ 데이터베이스에 전달
→ parse
→ plan
→ execute

애플리케이션과 데이터베이스가 분리되어 있다면 자연스러운 구조입니다. Query Builder는 여러 데이터베이스가 이해할 수 있는 SQL을 만들고, 데이터베이스는 전달받은 SQL을 자신의 실행 계획으로 바꿉니다.

GlueSQL은 파서(parser)와 플래너(planner), 실행 계층(executor)을 모두 같은 프로젝트 안에 가지고 있습니다. Query Builder가 내부 구조를 만든 뒤 이를 다시 SQL 문자열로 직렬화하고, GlueSQL이 그 문자열을 읽어 같은 구조를 복원할 필요가 없습니다.

GlueSQL에서는 두 입력 경로가 다음처럼 만납니다.

SQL → parse → translate ─┐
                         ├→ StatementPlan → planner → executor → storage
Query Builder ───────────┘

SQL은 파서와 translate 모듈을 거쳐 GlueSQL의 내부 표현으로 옮겨집니다. Query Builder는 Rust API로 같은 종류의 구조를 직접 만듭니다. 두 경로는 이후 동일한 플래너와 실행 계층을 사용합니다.

이 방향은 처음부터 코드에 드러나 있었습니다. 2022년 처음 추가된 AST Builder는 API에서 SQL 문자열을 생성하는 대신 GlueSQL AST를 직접 만드는 기능으로 소개되었습니다.

2026년에는 StatementPlan을 도입한 변경으로 SQL 문법을 나타내는 AST와 계획 및 실행에 필요한 표현을 나누기 시작했습니다. Query Builder의 주된 출력도 AST에서 StatementPlan으로 바뀌었고, 실제 역할에 맞춰 ast_builder를 query_builder로 변경했습니다.

ORM과는 다른 계층에서 시작했습니다

SeaORM과 같은 ORM은 애플리케이션의 엔티티(entity)와 관계(relation)를 데이터베이스의 테이블과 연결합니다. 모델 변환과 관계 조회, 마이그레이션(migration)처럼 애플리케이션에서 데이터를 관리하는 데 필요한 기능을 제공합니다. SeaORM이 사용하는 SeaQuery는 그 아래에서 데이터베이스에 전달할 SQL을 만듭니다.

현재 GlueSQL의 Query Builder는 엔티티나 관계를 정의하거나, Rust 모델을 테이블 스키마와 함께 관리하는 ORM 기능까지 제공하지는 않습니다. 지금까지는 ORM 계층보다 GlueSQL의 쿼리와 표현식(expression), 실행 계획을 구성하는 기능에 먼저 집중해왔습니다.

이 차이 때문에 기존 ORM의 Query Builder를 그대로 가져오는 것만으로는 목적을 달성하기 어렵습니다. 여러 데이터베이스에 공통으로 전달할 SQL이 아니라 다음과 같은 GlueSQL 전용 정보를 표현해야 하기 때문입니다.

  • GlueSQL이 지원하는 쿼리와 표현식
  • 인덱스 접근 경로와 JOIN 알고리즘 같은 명시적인 실행 결정
  • 스키마가 있는 테이블과 스키마리스 테이블을 함께 다루는 내부 표현
  • GlueSQL 플래너와 실행 계층의 변화에 맞춰 확장할 실행 계획

이 두 계층은 양자택일 관계가 아닙니다. 애플리케이션에서는 기존 ORM이 제공하는 모델과 관계 기능을 사용하고, 별도의 연결 계층을 통해 GlueSQL을 데이터베이스로 사용할 수도 있습니다. 현재 GlueSQL Query Builder의 중심 역할은 그보다 아래에서 엔진의 기능을 직접 사용하려는 코어 사용자를 위한 인터페이스에 가깝습니다.

개발자가 실행 계획을 명시할 수 있습니다

SQL에는 필요한 결과가 적혀 있지만 그 결과를 만드는 구체적인 방법은 적혀 있지 않습니다. 어떤 인덱스를 사용할지, JOIN을 어떤 알고리즘으로 실행할지는 보통 데이터베이스의 플래너가 결정합니다.

GlueSQL도 스키마와 스토리지 정보를 이용해 실행 방법을 자동으로 선택합니다. 앞으로 스토리지의 특성과 데이터 통계, 실행 비용을 함께 고려하려면 플래너에서 발전시킬 일이 많습니다. 서로 다른 환경을 같은 인터페이스로 연결하는 GlueSQL에서는 스토리지마다 사용할 수 있는 접근 방법과 비용도 다를 수 있습니다.

동시에 Query Builder는 개발자가 실행 방법을 직접 지정할 수 있는 경로를 제공합니다.

table("Player")
    .index_by(primary_key().eq("1"))
    .select()
    .build();

index_by는 사용할 인덱스를 실행 계획에 직접 기록합니다.

table("Player")
    .select()
    .join("PlayerItem")
    .hash_executor("PlayerItem.user_id", "Player.id")
    .project("Player.id, PlayerItem.name")
    .build();

hash_executor는 JOIN에 사용할 해시 실행 방식과 키 표현식(key expression)을 직접 구성합니다.

이 기능들은 SQL 쿼리 힌트(query hint)와 비슷해 보이지만 의미가 다릅니다. 힌트는 플래너가 참고하거나 무시할 수 있는 제안인 경우가 많습니다. GlueSQL Query Builder의 선택은 실행 계획의 일부로 만들어집니다. 실제로 index_by와 hash_executor는 SQL AST로 만들 수 없고, 실행 계획을 만들 때만 사용할 수 있습니다.

현재 GlueSQL이 실행 계획에 담는 실행 선택은 Query Builder에서도 직접 표현할 수 있습니다. SQL을 생성하는 API에 머무르지 않고, GlueSQL 전용 실행 계획을 개발자가 구성할 수 있도록 설계했습니다. 앞으로 실행 계획에 새로운 실행 방식이 추가될 때도 같은 인터페이스에서 직접 표현할 수 있습니다.

플래너가 만드는 자동 계획과 개발자가 명시하는 실행 계획은 서로 대체하는 기능도 아닙니다. 일반적인 쿼리는 플래너가 스토리지 정보를 바탕으로 계획하고, 실행 방법을 직접 제어해야 하는 코어 사용자는 Query Builder에서 필요한 결정을 제공할 수 있습니다. 플래너가 발전할수록 자동으로 선택할 수 있는 범위가 넓어지고, Query Builder도 표현할 수 있는 실행 계획을 함께 확장할 수 있습니다.

빌더를 상태 전이 그래프로 표현합니다

GlueSQL Query Builder의 또 다른 특징은 쿼리 작성 과정을 하나의 변경 가능한 빌더 구조체에 모두 담지 않는다는 점입니다.

일반적인 빌더 패턴(builder pattern)에서는 같은 빌더에 설정을 계속 추가하고 마지막 build()에서 조합을 확인할 수 있습니다. GlueSQL은 단계마다 다른 노드 타입(node type)을 반환하고, 각 노드가 다음에 이동할 수 있는 메서드를 제공합니다.

UPDATE의 일부 흐름을 단순화하면 다음과 같습니다.

UpdateNode
├→ UpdateSetNode
└→ UpdateFilterNode → UpdateSetNode

UpdateNode에서는 바로 set을 호출하거나 먼저 filter를 호출할 수 있습니다. filter를 사용하면 UpdateFilterNode가 되고, 값을 변경하는 set을 호출한 뒤에는 UpdateSetNode가 됩니다. 어떤 메서드를 다음에 사용할 수 있는지가 현재 노드 타입에 따라 달라집니다.

SELECT는 JOIN과 필터, 그룹화, 프로젝션, 정렬처럼 더 많은 경로를 가집니다. 각 노드가 허용하는 다음 전이를 메서드로 표현하면서 Query Builder 전체가 하나의 긴 메서드 목록보다 쿼리 구성 과정의 그래프에 가까워집니다.

이 구조는 Rust 컴파일러가 실제 테이블의 스키마나 컬럼 타입을 모두 검증한다는 뜻은 아닙니다. 존재하지 않는 컬럼이나 표현식의 타입은 여전히 플래너에서 확인해야 합니다. 대신 다음과 같은 구성 관계를 Rust 타입으로 표현할 수 있습니다.

  • 현재 단계에서 선택할 수 있는 다음 작업
  • SQL 절과 Query Builder 동작이 이어질 수 있는 순서
  • 특정 기능을 사용한 뒤 만들 수 있는 노드
  • build()할 수 있는 상태와 아직 구성이 필요한 상태

Query Builder의 타입 안전성(type safety)을 이야기할 때도 이 범위를 구분해야 합니다. 실제 데이터베이스 스키마 전체를 컴파일 단계에 검증하는 것이 아니라, 쿼리를 구성하는 상태와 전이를 타입 그래프로 나타내는 설계입니다.

구조화된 API와 SQL 표현식을 함께 사용합니다

GlueSQL Query Builder가 내부 실행 계획을 직접 만든다고 해서 항상 파서를 건너뛰는 것은 아닙니다.

다음 두 표현은 모두 사용할 수 있습니다.

table("Item")
    .select()
    .filter(col("price").gt(100))
    .filter("name = 'Lemon'")
    .project("id, name")
    .build();

col("price").gt(100)은 Query Builder 노드로 표현식을 구성합니다. 문자열로 전달한 name = 'Lemon'과 id, name은 파서와 translate를 이용해 GlueSQL 표현으로 바뀝니다.

파서를 없애는 것이 목적이었다면 두 방식을 섞을 필요가 없었을 것입니다. 하지만 모든 표현식을 처음부터 구조화된 API로 작성하도록 강제하면 간단한 조건도 길어질 수 있고, 아직 Query Builder API가 제공하지 않는 표현을 사용하기도 어렵습니다.

GlueSQL은 코어 사용자가 필요한 수준을 선택할 수 있게 합니다. 익숙한 SQL 표현식을 그대로 넣을 수도 있고, Rust API로 표현식과 실행 계획을 더 직접적으로 구성할 수도 있습니다. SQL과 Query Builder는 경쟁하는 두 인터페이스라기보다 같은 엔진으로 들어가는 서로 다른 입력 방식입니다.

플래너 테스트의 기대값도 같은 방식으로 작성합니다

Query Builder는 애플리케이션 코드뿐 아니라 플래너를 테스트할 때도 유용합니다. 플래너가 만든 실제 StatementPlan과 기대한 실행 계획을 비교하려면, 테스트에서도 기대값을 코드로 표현해야 합니다.

예를 들어 기본 키 계획 테스트에서는 SQL을 플래너에 전달해 실제 계획을 얻고, 기대하는 계획은 Query Builder로 다음처럼 작성합니다.

let sql = "SELECT * FROM Player WHERE id = 1;";
let actual = plan(&storage, sql);

let expected = table("Player")
    .index_by(primary_key().eq("1"))
    .select()
    .build()
    .unwrap();

assert_eq!(actual, expected);

SQL에는 결과 조건만 보이지만 기대값의 index_by에는 플래너가 기본 키 조회를 선택해야 한다는 결정이 드러납니다. 테스트를 읽는 사람도 SQL에서 만든 실제 계획과 Query Builder로 만든 기대 계획을 바로 비교할 수 있습니다.

Query Builder가 없다면 중첩된 AST와 실행 계획 구조체를 직접 조립하거나, 테스트만을 위한 별도의 DSL(domain-specific language)이나 빌더를 만들어야 합니다. 전자는 테스트에서 확인하려는 실행 결정이 내부 필드 사이에 묻히기 쉽고, 후자는 제품 코드와 별개로 또 하나의 표현 방식을 관리해야 합니다.

현재 primary_key, index, join 플래너 테스트에서는 Query Builder로 기대하는 실행 계획을 만듭니다. table, index_by, join과 같은 표현을 그대로 읽으며 플래너가 어떤 결정을 남겨야 하는지 확인할 수 있습니다.

같은 Query Builder가 코어 사용자를 위한 실행 계획 구성 API이면서, 플래너 테스트의 기대값을 읽기 좋게 만드는 공통 표현 역할도 하는 셈입니다.

Query Builder는 GlueSQL의 실행 구조를 여는 인터페이스입니다

GlueSQL이 기존 ORM이나 범용 Query Builder를 사용하지 못해서 같은 기능을 다시 만든 것은 아닙니다. 만들고자 한 결과가 SQL 문자열과 달랐습니다.

GlueSQL 전용 실행 계획을 직접 표현하고, 그 구성 과정을 Rust의 상태 머신과 타입 그래프로 나타내려면 엔진의 구조를 알고 있는 별도의 인터페이스가 필요합니다. SQL 표현식도 함께 사용할 수 있게 하면서 필요한 부분에서만 더 직접적인 제어를 선택할 수 있도록 했습니다.

GlueSQL의 Query Builder는 SQL을 대신하는 ORM이 아니라, GlueSQL의 실행 계획을 프로그래밍할 수 있게 여는 코어 인터페이스입니다.

플래너가 여러 스토리지에서 더 나은 실행 방법을 자동으로 찾는 방향으로 발전한다면, Query Builder는 같은 실행 구조를 개발자가 직접 표현하고 검증할 수 있는 방향으로 함께 발전할 수 있습니다. 두 경로가 같은 StatementPlan과 플래너, 실행 계층에서 만나는 점이 GlueSQL Query Builder의 가장 큰 특이점입니다.
