다시, 브라우저에서 쓰는 GlueSQL

최근 gluesql-js에 OPFS와 redb를 이용한 브라우저 저장소 지원을 배포했습니다. 페이지를 새로 열어도 데이터를 이어서 사용하고, 브라우저 안에서 SQL로 조회하고 다룰 수 있습니다.

이번 작업을 주도해 주신 @juhee200님은 저장소 구현뿐 아니라 배포 패키지, 예제, 브라우저 테스트, 여러 탭에서의 사용, 문서까지 함께 정리해 주셨습니다. 구현이 있다는 사실에서 한 걸음 더 나아가, 사용자가 무엇을 만들 수 있고 어떻게 시작하면 되는지까지 다룬 기여였습니다.

제게는 이 변화가 조금 특별합니다. GlueSQL을 처음 만들 때 하고 싶었던 일이 바로 브라우저에서 쓸 SQL 데이터베이스였기 때문입니다. 그때의 구상에 여러 사람의 관심과 작업이 더해지면서, 브라우저에서의 쓰임도 다시 구체적인 모습으로 다가왔습니다.

처음에는 브라우저에서 SQL을 쓰고 싶었습니다

GlueSQL을 구상하기 시작한 것은 2019년 가을이었고, 실제 코드를 쓰기 시작한 것은 그해 12월이었습니다. 프론트엔드와 백엔드를 개발하면서 SQL 데이터베이스도, NoSQL 데이터베이스도 사용하던 시기였습니다.

데이터를 다루다 보면 스키마를 잘 나누고 관계를 정리하는 것만으로도 문제가 훨씬 단순해지는 경우가 있습니다. 같은 정보를 여러 곳에 복사해 두는 대신 한곳에서 관리하고, 필요한 화면에서는 관계를 따라 조회하는 방식입니다. 그런데 백엔드에서는 트래픽이나 수평 확장 같은 조건 때문에 그런 구조를 그대로 유지하기 어려울 때도 있었습니다.

그렇다면 프론트엔드에서는 어떨까 생각했습니다. 브라우저에도 메모리와 저장 공간 등의 제약은 있지만, 수많은 사용자의 요청을 한꺼번에 처리하는 서버와는 조건이 다릅니다. 한 사용자가 다루는 데이터를 더 잘 정규화하고, SQL로 필요한 결과를 꺼내 쓰는 방식이 오히려 잘 맞을 수 있겠다는 생각이 들었습니다.

당시에도 브라우저에서 할 수 있는 일은 계속 늘고 있었습니다. 하지만 조금 복잡한 데이터를 다루려면 객체와 배열을 순회하고, 서로의 참조를 맞추고, 화면에 필요한 형태로 다시 조합하는 코드를 직접 작성하는 일이 많았습니다. 화면 상태를 관리하는 일과 별개로, 그 안에 들어갈 데이터를 다루는 도구가 더 있었으면 했습니다.

예를 들어 프로젝트와 할 일, 태그를 각각 관리하면서 특정 태그가 붙은 미완료 작업을 프로젝트별로 모아 보고 싶을 수 있습니다. 이런 관계를 매번 자바스크립트 코드로 조합하는 대신, 테이블을 나누고 JOIN과 집계로 조회할 수 있다면 편리하겠다고 생각했습니다.

개인적으로 Rust를 적극적으로 써보고 싶었던 마음도 컸습니다. Rust는 WebAssembly를 지원하니, Rust로 SQL 엔진을 만들고 브라우저에서 실행할 수 있겠다는 구상이 이어졌습니다. 제가 쓰고 싶은 것이면서, 오픈소스로 공개했을 때 다른 사람도 관심을 가질 만한 작업으로 보였습니다.

초기에는 브라우저에서 SQL을 직접 실행해 볼 수 있는 데모를 만들어 공개했습니다. 당시 Rust 커뮤니티에 GlueSQL을 소개할 때도 웹에서 바로 써볼 수 있다는 점을 많이 이야기했습니다.

다만 저장소를 연결하는 인터페이스를 나누고 보니 웹에만 한정할 이유는 없었습니다. 데이터를 어디에 보관하든 정해진 인터페이스로 연결하면 같은 SQL 엔진을 사용할 수 있겠다는 방향으로 일찍 확장했습니다. GlueSQL의 이름에 들어간 Glue도 그렇게 SQL과 여러 저장소를 이어 붙이는 역할과 연결되어 있습니다.

가능성은 남아 있었지만, 우선순위는 밀렸습니다

자바스크립트 지원을 없앤 것은 아니었습니다. npm으로 배포했고, 메모리와 localStorage, sessionStorage를 지원한 뒤 IndexedDB도 연결했습니다. 다만 SQL 엔진과 다른 저장소 등 신경 쓸 부분이 늘어나면서 자바스크립트 쪽은 점점 우선순위가 밀렸습니다.

IndexedDB에 대한 제 경험도 영향을 주었습니다. 요청을 보내고 이벤트로 결과를 받는 API는 예전 웹 개발 방식처럼 느껴졌습니다. Rust에서 사용할 수 있도록 감싼 라이브러리를 이용했지만, 그 아래의 사용 규칙까지 사라지는 것은 아니었습니다.

특히 트랜잭션을 다루는 방식이 번거로웠습니다. 예를 들어 트랜잭션 안에서 값을 읽은 뒤 네트워크 요청 같은 다른 비동기 작업을 기다리면, 다시 기록하려 할 때는 트랜잭션이 이미 끝나 있을 수 있습니다. 래퍼로 호출을 간단하게 만들어도 이런 트랜잭션의 수명 규칙은 계속 신경 써야 했습니다. IndexedDB가 제공하는 기능과 별개로, 이 방식에 맞춰 개발을 계속하고 싶은 마음은 잘 생기지 않았습니다.

그러던 중 OPFS라는 선택지가 생겼습니다. OPFS는 Origin Private File System의 약자로, 웹사이트가 브라우저 안의 자기 저장 공간에 파일을 읽고 쓸 수 있는 기능입니다. 사용자의 일반 폴더를 직접 여는 기능이 아니라, 해당 사이트에 속한 파일 공간을 사용하는 방식입니다.

브라우저에서 파일을 읽고 쓸 수 있다면, IndexedDB와는 다른 방식으로 저장소를 만들 수 있겠다는 기대가 생겼습니다. 당시에는 구체적인 구현 방식까지 살펴본 것은 아니었습니다. 그래도 다른 접근이 가능해 보이니, IndexedDB 쪽에 다시 많은 시간을 들이고 싶은 마음은 오히려 줄었습니다.

다만 OPFS는 파일을 다루는 기능이지 데이터베이스는 아닙니다. 데이터베이스로 쓰려면 데이터를 어떤 형식으로 저장하고 조회할지, 트랜잭션은 무엇으로 처리할지부터 정해야 했습니다. 그 부분은 아직 구체화하지 못했고, 다른 작업에 집중하는 동안 바로 구현에 들어가지는 못했습니다.

그 사이에도 자바스크립트 지원은 다른 기여자들의 관심 속에서 계속 발전하고 있었습니다. @miinhho님은 Node.js 바인딩에 napi-rs를 도입하는 작업을 진행해 주셨습니다. 서로 다른 사용 환경에 대한 관심이 프로젝트의 다음 작업으로 이어지고 있었습니다.

OPFS를 연결하고, 실제로 쓸 수 있는 형태로 만들었습니다

@juhee200님의 작업은 브라우저에서 SQL을 별도 작업 스레드로 실행할 수 있도록 Web Worker 기반을 마련하는 일부터 시작했습니다. 이후 OPFS와 redb를 연결하는 저장소 구현으로 이어졌습니다.

세 구성 요소의 역할을 나눠 보면 이해하기 쉽습니다. OPFS는 브라우저 안에서 파일을 읽고 쓰는 방법을 제공합니다. redb는 그 파일에 데이터를 저장하고 트랜잭션을 처리하는 데이터베이스 엔진입니다. GlueSQL은 그 위에서 테이블과 SQL을 다룹니다. 브라우저용 SQL 엔진을 새로 만드는 대신, GlueSQL과 redb가 이미 맡고 있던 일을 브라우저의 파일 공간까지 연결한 것입니다.

사용자는 브라우저에 데이터를 저장하기 위해 서버부터 마련할 필요가 없습니다. 메모나 작업 기록을 로컬에 보관하고, 다음에 페이지를 열었을 때 이어서 조회할 수 있습니다. SQL은 Web Worker에서 실행하므로 화면을 처리하는 주 스레드와도 분리됩니다. 저장 공간은 브라우저가 관리하므로 사이트 데이터 삭제나 저장 용량 정책의 영향은 받습니다.

여기서 구현이 끝나지는 않았습니다. @juhee200님은 npm 패키지에서 OPFS를 바로 가져다 쓸 수 있도록 구성하고, 필요한 Worker와 WebAssembly 파일도 패키지에 포함해 주셨습니다. 사용자가 Rust 쪽을 직접 빌드하지 않아도 설치한 패키지에서 시작할 수 있게 된 것입니다.

직접 실행해 볼 수 있는 OPFS 예제도 함께 준비되었습니다. 예제의 방문 횟수는 페이지를 새로고침해도 유지됩니다. SQL을 직접 입력해 결과나 오류를 확인할 수도 있습니다.

이 예제에는 브라우저 테스트도 구성되어 있습니다. 데이터를 기록한 뒤 페이지를 새로고침하고 다시 읽어, 저장한 값이 유지되는지 자동으로 확인합니다.

사용자는 탭 하나만 열지 않습니다

브라우저에서 데이터베이스를 연 뒤 쿼리가 잘 실행되는 것만으로는 충분하지 않았습니다. 사용자는 같은 앱을 여러 탭에서 열기도 합니다. 한쪽에서 기록한 내용을 다른 탭에서도 조회하고, 먼저 열었던 탭을 닫은 뒤에도 남은 탭을 계속 사용할 수 있기를 기대합니다.

이번 저장소에서 사용하는 OPFS 파일 접근 방식에는 한 번에 한 실행 환경이 파일을 맡아야 하는 제약이 있습니다. 탭마다 같은 데이터베이스를 따로 열려고 하면, SQL과 관계없는 이 제약을 애플리케이션 개발자가 직접 해결해야 합니다.

@juhee200님은 여러 탭이 같은 데이터베이스를 사용하도록 하는 작업도 이어가 주셨습니다. 한 탭이 데이터베이스를 맡고 다른 탭의 요청을 함께 처리하며, 그 탭이 닫히면 다른 탭이 역할을 이어받는 방식입니다. 브라우저 테스트에서도 여러 탭의 동시 사용과 담당 탭이 닫히는 상황을 확인합니다.

이 기능은 gluesql/opfs/shared로 제공하며, 현재는 실험적 지원입니다. 처리 중 담당 탭이 사라진 요청은 적용 여부를 확정할 수 없어 오류로 반환될 수 있으므로, 그런 쓰기 요청을 다시 시도하는 방법은 앱에서도 고려해야 합니다. 지원 환경과 사용 시 주의할 점은 README의 여러 탭 지원 안내에 정리되어 있습니다.

문서도 사용자 관점에서 다시 정리되었습니다. 개편된 README는 프로젝트 내부 구조보다 어떤 앱을 만들 수 있는지부터 설명합니다. 데이터의 성격에 맞는 저장소를 고르고, 자신의 환경에서 시작하는 방법도 안내합니다.

잠깐 쓰고 버릴 데이터는 메모리에, 작은 설정은 Web Storage에, 다음에도 이어서 사용할 기록은 OPFS에 두는 식입니다. 여러 탭에서 함께 쓴다면 어떤 진입점을 선택해야 하는지도 이어서 안내합니다. 기능을 잘 아는 사람의 설명에서, 처음 쓰는 사람이 선택하고 시작할 수 있는 설명으로 바뀌었습니다.

이번 기여가 특히 반가운 이유도 여기에 있습니다. OPFS라는 새 API를 붙이는 데서 멈추지 않고, 설치한 사람이 실제로 사용하다 마주칠 문제까지 다룬 작업이었습니다. 저장소 구현, 패키지 구성, 예제, 테스트, 여러 탭 지원, 문서는 각각 다른 변경이지만 사용자에게는 모두 하나의 사용 경험입니다.

브라우저에서 시작해, 서로 다른 저장소까지

브라우저 안에서 SQL 데이터베이스를 사용하는 방향은 GlueSQL만의 이야기는 아닙니다. SQLite의 WebAssembly 배포도 OPFS를 지원합니다. 데이터를 서버에만 두지 않고 브라우저에도 보관하면서, 로컬에서 조회하고 편집할 수 있는 앱을 만들 기반이 마련되고 있습니다.

GlueSQL에는 이 흐름과 잘 맞으면서도 조금 다른 특성이 있습니다. SQL 엔진과 저장소가 분리되어 있다는 점입니다. 브라우저에서는 OPFS와 redb를 이용하고, 서버의 Rust 환경에서는 MongoDB, Redis, 파일 등 다른 저장소를 연결해 같은 GlueSQL 엔진을 사용할 수 있습니다.

가령 브라우저에는 사용자가 작업 중인 데이터를 보관하고, 서버에는 여러 사람이 공유할 데이터를 둘 수 있습니다. 두 쪽의 저장 방식이 달라도 같은 SQL 엔진을 바탕으로 데이터를 다루는 구성을 생각해 볼 수 있습니다. 이런 구조에서 브라우저와 서버 사이의 동기화나 충돌 해결까지 이번에 제공하는 것은 아니지만, 그 위에 어떤 앱을 만들 수 있을지는 훨씬 구체적으로 상상할 수 있게 되었습니다.

여기서 서버의 다양한 저장소 지원은 Rust용 GlueSQL의 기능입니다. 자바스크립트 패키지의 Node.js 지원은 현재 메모리 저장소를 사용합니다. 환경별 지원 범위가 같지는 않지만, SQL 엔진을 한 저장 방식에 묶어 두지 않았던 설계가 브라우저에서도 다시 의미를 갖게 되었다고 느낍니다.

처음에는 브라우저에서 SQL을 쓰고 싶어 시작했지만, 여러 사람의 기여가 쌓이며 다양한 저장소를 연결하는 엔진으로 발전해 왔습니다. 이제 그동안 쌓인 엔진과 저장소의 기능을 다시 브라우저에서 활용할 수 있게 되었습니다. 자바스크립트 지원을 부가적인 바인딩 하나로만 두기에는, GlueSQL이 이 환경에서 제공할 수 있는 가치가 분명하다고 생각합니다.

함께 만들어가는 GlueSQL

이번 작업을 거쳐 OPFS 지원은 npm의 gluesql 0.20.0 패키지로 배포되었습니다. OPFS 예제에서 저장과 조회를 직접 해보고, README에서 자신의 환경에 맞는 시작 방법을 확인할 수 있습니다.

이번 변화는 오래된 구상 하나가 구현된 것 이상으로 느껴집니다. @juhee200님의 작업을 통해 저장소를 어디에 연결할지뿐 아니라, 사용자가 여러 탭에서 어떻게 쓰고 처음 설치한 뒤 어디서 시작할지까지 함께 구체화할 수 있었습니다.
