GlueSQL의 쿼리 계획이 실행 파이프라인으로 바뀌었습니다

지난 플래너 개요에서는 GlueSQL의 실행 계획이 SQL 절을 나열한 형태에서 실제 실행 순서가 드러나는 구조로 옮겨가고 있다고 설명했습니다. 이어서 Query Builder가 GlueSQL 전용 실행 계획을 직접 만들고, 쿼리 구성 순서를 타입 그래프로 표현한다는 점도 살펴봤습니다.

2026년 8월 6일 병합된 Pull Request #1937은 이 두 흐름을 실제 쿼리 실행 구조에서 연결합니다. SELECT와 VALUES의 QueryPlan을 타입으로 표현한 실행 파이프라인(typed execution pipeline)으로 바꾸고, Query Builder와 플래너, 실행 계층도 같은 구조를 사용하도록 정리했습니다.

이번 변경은 178개 파일에 걸쳐 이루어졌습니다. 하지만 핵심은 파일 수보다 간단합니다.

실행 순서가 실행 계층의 코드 안에만 있지 않고, 실행 계획의 타입 구조에 직접 드러나게 되었습니다.

이전 계획은 SQL 문법의 형태를 닮아 있었습니다

StatementPlan은 SQL parser의 AST와 실행 계층을 분리하기 위해 도입되었습니다. 그러나 이전 QueryPlan은 여전히 SQL 문법의 구성을 많이 닮아 있었습니다.

구조를 단순화하면 다음과 같습니다.

QueryPlan
├─ body
├─ order_by
├─ limit
└─ offset

SelectPlan
├─ distinct
├─ projection
├─ from
├─ selection
├─ group_by
└─ having

이 구조를 보면 쿼리에 어떤 SQL 절이 있는지는 알 수 있습니다. 하지만 각 절이 어떤 순서로 실행되는지는 계획만 보고 바로 알기 어렵습니다.

실제 순서는 SELECT를 실행하는 하나의 큰 함수 안에 있었습니다. 테이블에서 행을 읽고 JOIN과 필터를 적용한 뒤, 집계와 projection, 정렬과 DISTINCT, OFFSET과 LIMIT을 차례로 처리했습니다.

실행 계획(QueryPlan): SQL 절(clause)과 설정을 모아 둠
실행 계층(executor): 계획을 읽고 실제 실행 순서를 결정함

계획과 실행이 분리되어 있어도 실행 계층이 SQL 절의 관계를 다시 해석해야 했습니다. 새로운 실행 방법을 추가하거나 순서를 바꿀 때는 계획의 필드뿐 아니라 전체 실행 흐름도 함께 살펴야 했습니다.

경계가 흐리면 리뷰 비용도 커집니다

메인테이너 입장에서 이 작업을 서두른 현실적인 이유는 Pull Request를 검토하며 플래너와 실행 계층 사이의 책임을 어디에 두어야 할지 혼동하는 경우를 반복해서 보았기 때문입니다.

실행 전에 결정할 수 있는 내용도 기존 계획에 들어갈 자리가 분명하지 않으면, 실제 쿼리가 동작하는 실행 계층에 구현하기 쉽습니다. 그러면 실행 계층은 계획에 적힌 연산을 수행하는 일뿐 아니라 SQL의 의미를 다시 해석하고 실행 방법을 선택하는 일까지 맡게 됩니다. 기능이 추가될수록 실행 계층이 무거워지고, 다음 작업도 같은 위치에 코드를 더하는 방향으로 이어질 수 있습니다.

이는 개별 기여자의 구현 방식만으로 볼 문제가 아닙니다. 기존 구조가 책임의 위치를 충분히 안내하지 못했다면, 처음 코드를 접하는 사람에게 어느 계층이 맞는지 판단하라고 요구하기 어렵습니다.

경계가 모호하면 리뷰할 때도 구현의 옳고 그름뿐 아니라 그 책임이 어느 계층에 있어야 하는지 함께 판단해야 합니다. 동작하는 코드를 다른 계층으로 옮기고 테스트를 다시 구성하거나, 비슷한 설계 논의를 여러 Pull Request에서 반복하는 비용도 생깁니다.

그래서 더 많은 기능을 쌓기 전에 먼저 교통정리가 필요했습니다.

Planner
→ SQL과 스키마, 스토리지 정보로 실행 전에 가능한 결정을 남김

Executor
→ 계획에 기록된 노드를 실제 데이터에 적용함

이번 파이프라인만으로 두 계층의 모든 경계가 완성된 것은 아닙니다. 다만 실행 순서와 각 결정이 들어갈 노드가 계획에 드러나면서, 실행 계층이 새로운 판단까지 떠맡지 않도록 하는 방향을 구조로 보여줄 수 있게 되었습니다.

앞으로 코드를 추가할 때도 먼저 “이것은 실행 전에 정할 계획인가, 실제 행을 처리할 연산인가”를 구분할 수 있습니다. 기여자가 기능을 넣을 위치를 찾기 쉬워지고, 메인테이너도 같은 기준으로 변경을 검토할 수 있다는 점이 이번 개편의 중요한 목적입니다.

실행 순서를 계획으로 옮겼습니다

이번 변경 뒤의 QueryPlan은 Project, Values, SelectOrderBy, Distinct, Offset, Limit처럼 실행 단계가 되는 variant를 가집니다. 각 단계는 바로 앞에서 실행할 계획을 input으로 받습니다.

다음 쿼리를 예로 들어보겠습니다.

SELECT DISTINCT team_id, COUNT(*) AS player_count
FROM Player
WHERE active = TRUE
GROUP BY team_id
ORDER BY player_count DESC
OFFSET 5
LIMIT 10;

새로운 계획 구조를 개념적으로 단순화하면 다음과 같습니다.

Limit(10)
└─ Offset(5)
   └─ Distinct
      └─ SelectOrderBy(player_count DESC)
         └─ Project(team_id, COUNT(*) AS player_count)
            └─ Aggregation(GROUP BY team_id)
               └─ Filter(active = TRUE)
                  └─ Source(Player)

가장 안쪽의 Source가 먼저 실행되고, 그 결과가 바깥 단계로 전달됩니다. 마지막에는 가장 바깥의 Limit이 앞 단계에서 받은 결과를 10개로 제한합니다.

이제 실행 순서는 별도의 함수 안에만 존재하지 않습니다. 계획을 안쪽부터 따라가는 것만으로 어떤 연산이 어떤 순서로 실행되는지 확인할 수 있습니다.

타입이 가능한 연결 관계를 제한합니다

모든 실행 단계를 하나의 범용 노드로 만들고 자유롭게 연결할 수도 있습니다. GlueSQL은 그 대신 각 단계가 받을 수 있는 입력을 구체적인 enum으로 표현했습니다.

예를 들어 FilterInputPlan에는 다음 입력만 올 수 있습니다.

enum FilterInputPlan {
    Source(SourcePlan),
    InnerJoin(Box<InnerJoinPlan>),
    LeftOuterJoin(Box<LeftOuterJoinPlan>),
}

필터는 테이블과 같은 source 또는 JOIN의 결과를 입력으로 받습니다. LIMIT이나 projection의 결과를 필터 앞에 잘못 연결할 수 있는 variant는 없습니다.

반대로 LimitInputPlan에는 projection과 정렬, DISTINCT, OFFSET 등의 결과가 들어올 수 있습니다. OFFSET 뒤에 LIMIT을 놓을 수 있지만 LIMIT 뒤에 다시 필터를 놓는 관계는 타입으로 표현할 수 없습니다.

이 제약은 쿼리의 의미를 모두 Rust 컴파일러가 검증한다는 뜻은 아닙니다. 컬럼의 존재 여부와 표현식 타입처럼 실제 스키마가 필요한 판단은 여전히 플래너가 담당합니다. 여기에서 타입이 보장하는 것은 실행 단계 사이의 구조적인 연결 관계입니다.

SELECT와 VALUES도 필요한 단계가 다르므로 별도의 경로를 가집니다.

SELECT: Source → Join → Filter → Aggregation → Project
        → Order By → Distinct → Offset → Limit

VALUES: Values → Order By → Offset → Limit

VALUES에는 테이블 source나 JOIN, 필터와 집계가 필요하지 않습니다. 모든 단계를 하나의 범용 그래프에 넣는 대신 실제로 허용되는 경로를 구체적인 타입으로 나누었습니다.

실행 계층도 같은 파이프라인을 따라갑니다

이전에는 SELECT 실행 함수가 JOIN과 필터, 집계, projection과 정렬을 한곳에서 순서대로 호출했습니다. 새로운 실행 계층은 계획과 같은 단위로 모듈이 나뉩니다.

LimitPlan을 실행할 때는 먼저 input에 담긴 계획을 실행하고, 받은 행에 take를 적용합니다. FilterPlan은 source나 JOIN을 실행한 뒤 조건에 맞는 행을 남깁니다. ProjectPlan은 자신에게 올 수 있는 입력을 실행한 뒤 출력할 값을 구성합니다.

각 실행 노드
1. 자신의 input을 실행함
2. 받은 결과에 자신이 맡은 연산을 적용함
3. 결과를 바깥 노드로 전달함

전체 실행 순서를 하나의 함수가 지휘하는 대신 계획의 바깥 노드가 안쪽 노드를 실행합니다. 계획의 구조와 실행 코드의 구조가 같은 방향을 보게 된 것입니다.

이렇게 나누면 각 실행 노드가 맡을 책임도 작아집니다. LIMIT 구현은 JOIN이나 집계의 실행 순서를 알 필요가 없고, source 구현은 자신의 결과가 나중에 정렬되거나 제한되는지 알 필요가 없습니다.

플래너의 결정은 실행할 노드에 남습니다

파이프라인은 SQL 절의 순서만 표현하지 않습니다. 플래너가 선택한 구체적인 실행 방법도 그 연산을 수행할 노드에 기록합니다.

테이블 source의 TableAccessPlan은 현재 다음과 같은 접근 방법을 표현합니다.

enum TableAccessPlan {
    FullScan,
    PrimaryKey { /* ... */ },
    Index { /* ... */ },
}

처음 쿼리를 계획으로 옮기면 테이블 source는 전체 스캔으로 시작합니다. 플래너가 기본 키 조건이나 사용할 수 있는 인덱스를 찾으면 같은 source 노드의 접근 방법을 바꿉니다. 실행 계층은 그 결정을 보고 scan_data, fetch_data, scan_indexed_data 가운데 필요한 스토리지 동작을 사용합니다.

JOIN도 nested loop와 hash join을 별도의 계획 노드로 표현합니다. 플래너가 hash join을 선택하면 실행 방법에 관한 정보가 JOIN을 실행할 노드에 자리 잡습니다.

이는 플래너가 내린 판단과 실행 계층이 수행할 작업의 연결을 더 직접적으로 만듭니다. 어떤 결정이 실제로 어디에서 사용되는지 찾기 위해 여러 SQL 절과 하나의 큰 실행 함수를 함께 추적할 필요가 줄어듭니다.

Query Builder도 같은 관계를 표현합니다

GlueSQL의 Query Builder는 SQL 문자열이 아니라 StatementPlan을 직접 만듭니다. 이번 변경에서는 Query Builder의 각 노드도 새로운 쿼리 파이프라인과 같은 연결 관계를 따르도록 바뀌었습니다.

Query Builder에서 source를 선택하고, JOIN과 필터, projection, 정렬과 LIMIT을 이어가는 과정은 실행 계획의 노드를 구성하는 과정이기도 합니다. 현재 단계에서 호출할 수 있는 다음 메서드가 Rust 타입에 따라 달라지고, 최종적으로 만들어지는 계획도 같은 순서의 타입 구조를 가집니다.

Query Builder의 타입 전이
          ↓
QueryPlan의 실행 노드
          ↓
executor의 실행 순서

지난 글에서 살펴본 Query Builder의 타입 그래프가 사용자 API에만 적용된 별도의 규칙이 아니라, GlueSQL의 실제 실행 구조와 맞물리게 되었습니다. 플래너 테스트에서 Query Builder로 기대하는 계획을 작성할 때도 실행 계층이 사용할 구조를 더 직접적으로 비교할 수 있습니다.

변경 범위가 컸던 이유

QueryPlan은 여러 계층이 공유하는 경계입니다. 구조가 바뀌면 한 모듈만 수정해서는 동작을 유지할 수 없습니다.

  • SQL의 AST를 새로운 QueryPlan으로 옮기는 과정
  • Query Builder가 같은 계획을 직접 만드는 과정
  • 기본 키와 인덱스, JOIN과 집계를 계획하는 과정
  • 만들어진 각 노드를 실제로 실행하는 과정
  • SQL fixture와 Query Builder를 이용해 결과를 검증하는 test suite

이번 Pull Request에서 planner와 executor, Query Builder와 test suite까지 큰 변경이 함께 일어난 이유입니다. 단순히 이름을 바꾸거나 파일을 나눈 것이 아니라, 이 계층들이 주고받는 공통 표현을 바꾼 작업이었습니다.

모든 statement가 한 번에 바뀐 것은 아닙니다

이번 변경은 SELECT와 VALUES의 쿼리 파이프라인을 완성하는 데 초점을 맞췄습니다. INSERT ... SELECT처럼 QueryPlan을 입력으로 사용하는 경로도 새로운 파이프라인을 이용합니다.

하지만 UPDATE와 DELETE를 비롯한 statement-level DML 전체가 같은 노드 구조로 바뀐 것은 아닙니다. 컬럼 참조와 출력 메타데이터를 계획 단계에서 더 확정하는 일, 더 다양한 접근 경로와 JOIN 계획을 표현하는 일도 앞으로 발전시킬 수 있는 영역으로 남아 있습니다.

이 변경을 곧바로 쿼리 속도가 빨라졌다는 의미로 읽을 필요도 없습니다. 같은 SQL을 실행하더라도 실행 계획과 실행 계층의 책임을 더 분명하게 만들기 위한 구조 개편이 중심입니다.

실행 구조를 다음 단계로 옮길 기반을 만들었습니다

이전 계획도 GlueSQL의 쿼리를 실행할 수 있었습니다. 이번 작업의 가치는 가능하지 않던 SQL 하나를 새로 실행하게 된 데 있기보다, 이후의 변화를 담을 구조를 마련했다는 데 있습니다.

실행 순서가 계획에 드러나면 플래너는 어떤 노드를 바꾸고 어떤 결정을 남길지 더 명확하게 다룰 수 있습니다. 실행 계층은 SQL 문법의 여러 필드를 다시 조합하는 대신 자신이 받은 노드를 실행하는 데 집중할 수 있습니다. 새로운 실행 방법을 추가할 때도 그 방법이 들어갈 위치와 허용할 입력 관계를 타입으로 표현할 수 있습니다.

2026년 초에 StatementPlan을 도입하며 시작한 AST와 실행 표현의 분리는 이번 쿼리 파이프라인을 통해 한 단계 더 구체적인 형태가 되었습니다.

GlueSQL의 쿼리 계획은 이제 실행에 필요한 SQL 절을 모아 둔 구조가 아니라, 실행 순서와 연결 관계를 직접 표현하는 파이프라인입니다.

이 기반 위에서 플래너가 더 많은 의미와 실행 결정을 맡고, 여러 스토리지에 맞는 실행 방법을 선택하며, 실행 계층의 각 연산을 더 분명하게 나누는 작업을 이어갈 수 있습니다.
